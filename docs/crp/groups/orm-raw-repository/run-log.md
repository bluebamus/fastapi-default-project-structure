  요구한 "전 path operation async 검사 + 금지 동기 I/O 정적 검사" 는 이 저장소에 만들어진 적이 없다.
  아홉 라운드가 그 칸을 통과로 선언했고 아무 검사도 빨개지지 않았다.
  **열린 상자가 우연히 정직했던 것이다.** 누군가 성실하게 12칸을 `[x]` 로 바꿨다면 F-025 는
  영영 닫힌 상자 뒤에 있었을 것이다. 이것이 "표시만 바꾸지 말라" 는 규칙의 진짜 이유다 —
  단정함의 문제가 아니라, 근거를 대조하는 행위 자체가 유일한 발견 수단이기 때문이다.
  F-025 를 실측하니 코드는 INV-10 을 지키고 있었다(path operation 36개 전부 async, 블로킹 호출 0).
  그래서 이 결함의 심각도는 "지금 깨져 있다" 가 아니라 **"깨져도 아무도 모른다"** 에서 온다.
  동기 `def` path operation 은 FastAPI 가 threadpool 로 넘겨 주므로 **틀리게 동작하지 않는다** —
  테스트도 리뷰도 통과한다. 드러나는 시점은 부하가 걸려 threadpool 이 마를 때이고, 그때는 원인을
  이 파일에서 찾지 않는다. HIGH 로 매긴 이유가 이것이다.
- **절차 관찰:** 문서를 쓰는 스크립트의 `print` 가 em dash 를 cp949 로 못 써서 죽었다 — F-017 과
  같은 계열이다. 파일 쓰기는 끝난 뒤였으므로 산출물은 멀쩡했지만, 순서가 반대였다면 절반만 쓰인

  스크립트는 그 보호 밖에 있다**. 검수 장치만 UTF-8 이면 검수는 안전하고 작업은 안전하지 않다.

### 추세 해석 — 정직하게

심각도가 단조 감소하지 않는다. R-4 에서 CRIT 이 다시 나왔고 R-6 에서 HIGH 가 나왔다.
**이것이 정상이다** — 각 라운드가 검사한 범위가 다르기 때문이다. R-4 는 새로 만든 계층을,
R-6 은 검수 장치 자신을 처음 봤다. "라운드가 갈수록 결함이 줄어든다"는 곡선은 **같은 범위를
반복해서 볼 때만** 의미가 있고, 여기서는 매 라운드 새 영역이 들어왔다.

R-10 에서 HIGH 가 다시 나온 것도 같은 이유다 — 이번에 처음 검사한 범위가 **게이트가 요구했지만 만들어지지 않은 검사** 였다. 아홉 라운드 동안 초록이던 칸이 열 번째에 빨개진 것이 아니라, 열 번째에야 그 칸을 **처음 봤다**.

수렴의 근거는 추세선이 아니라 **결정적 게이트**다 — 정적분석 · 계층 불변식 · 공개 API 불변이
전부 그린이고 Open 인 Fix 가 0건이다. 확률적 리뷰의 "훑어봤는데 문제없음" 은 수렴 증거가
아니므로 이 표의 0 도 "더 없다"는 뜻이 아니라 "이 검사들로는 더 안 나온다"는 뜻이다.
검사하지 않은 범위는 `residual-risk.md` 하단에 명시했다.
