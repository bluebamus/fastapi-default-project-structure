1. 전체 흐름과 읽는 방법

이 문서는 fastapi-default-project-structure의 2026-09-17 작업 트리를 기준으로 한다. 서버 실행 시 한 번 준비되는 과정과 요청마다 반복되는 과정을 나눠 설명한다. 설정은 모듈 import 과정에서 만들어지고 실제 Redis 검증·개발용 DDL은 ASGI 서버가 lifespan에 진입한 뒤 실행된다. 따라서 manage_application_resources()는 설정 생성 이후에 호출된다.

설정 객체 ≠ 로깅 적용 ≠ DB 엔진 생성 ≠ 실제 네트워크 접속 ≠ 요청별 세션. 각 단계의 순서와 소유권을 구분한다.

코드 근거 링크는 저장소 루트 기준이다. 로컬 HTML에서 Python 파일은 브라우저 정책에 따라 표시 또는 다운로드될 수 있다. 예시와 실제 구현을 구분하고, 확인하지 않은 외부 시스템과 구현상의 제한을 함께 표시한다.

코드 근거: config.py · get_app_settings · main.py · lifespan · app/core/resources.py · manage_application_resources

2. 실행 진입점과 프로세스 경계

python main.py는 먼저 import·앱 조립을 실행하고 run_server()에서 uvicorn.run()을 호출한다. uvicorn main:app는 실행기가 main의 app을 import한다. 두 경로는 정상 ASGI lifespan을 사용하면 같은 자원 관리 경로에 진입한다. --lifespan off는 Redis ping·자원 관리를 건너뛰므로 정상 운영 경로로 취급하지 않는다.

직접 실행은 SERVER_HOST·SERVER_PORT·reload=app_settings.DEBUG·setup_uvicorn_logging()을 넘긴다. CLI 바인딩·reload는 CLI 옵션이다. DEBUG=true만으로 임의의 Uvicorn CLI에 reload가 자동 적용되지는 않는다.

reload나 여러 worker는 새 프로세스에서 import·lifespan을 다시 수행할 수 있다. “설정 한 번”은 배포 전체가 아니라 프로세스 모듈 상태 기준이다. API worker마다 Redis client·DB pool이 있고 Celery는 별도 프로세스이다.

저장소 루트 실행 예시 — 이 명령을 문서 작성 중 자동 실행하지 않음

uv run python main.py
# CLI 옵션은 별도로 지정
uv run uvicorn main:app --host 127.0.0.1 --port 8000

코드 근거: main.py · app/utils/logs/setup.py · setup_uvicorn_logging

3. .env → 타입 검증 → 캐시된 설정 객체

config.py의 각 BaseSettings subclass는 SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="ignore")를 선언한다. 하나의 딕셔너리를 다른 클래스에 복사하는 것이 아니라 각 인스턴스가 자기 필드를 해석한다. 현재 getter의 기본 생성에서는 운영체제 환경변수 → 현재 작업 디렉터리의 .env → Field 기본값이 우선순위이다. 명시적 생성자 인자를 전달하면 일반적으로 그것이 환경값보다 먼저지만 전역 getter는 인자 없이 생성한다. Pydantic Settings 공식 근거.

.env의 상대 경로는 작업 디렉터리에 의존한다. .env.example은 복사용 참고 파일이며 자동 fallback이 아니다. .env가 없으면 기본값으로 설정을 만들 수 있어도 그 기본 주소의 DB·Redis가 준비됐다는 뜻은 아니다.

DEBUG=false문자열은 bool 파싱 후 Python False가 된다. 리스트는 CORS_ALLOW_ORIGINS=["http://localhost:3000"]처럼 JSON 배열로 지정한다. 타입 오류·validator 위반은 config import를 실패시켜 lifespan 전에 기동을 막을 수 있다.

@lru_cache가 붙은 get_app_settings()·get_db_settings()등이 객체를 재사용한다. 파일 끝의 app_settings = get_app_settings()등은 import 시 전역 참조를 즉시 만든다. 요청마다 .env를 다시 읽지 않는다. 실행 중 파일 변경은 기존 객체를 갱신하지 않는다. 테스트에서 캐시만 비워도 다른 모듈이 이미 가져온 전역 참조까지 교체되지는 않으므로 새 프로세스 또는 통제한 monkeypatch로 확인한다.

코드 근거: config.py · .env.example

5. 로그 레벨은 어디에서 어떻게 적용되는가

첫 get_logger()가 configure_logging()을 호출한다. _configured가 이미 참이면 일반 재호출은 생략한다. 최초 적용은 dictConfig(build_dictconfig())이다. config는 LOG_LEVEL·LOG_CONSOLE_LEVEL 원설정과 계산 메서드를 보관하며 유효 레벨 계산·logging 객체 적용은 로그 구성 단계에서 수행한다.

실제 코드 발췌

logger.info("[startup] 애플리케이션 자원 초기화 시작 (DEBUG=%s)", app_settings.DEBUG)

마지막 app_settings.DEBUG는 %s 자리에 표시할 값이다. 레벨은 logger.info가 정한 INFO이고 이 값은 출력 조건·레벨 설정 인자가 아니다. DEBUG=false여도 INFO를 허용하면 (DEBUG=False)가 출력된다. 진단 정보로는 의미가 있지만 정책 적용에는 필요 없다. 제거하려면 (DEBUG=%s)도 함께 제거해야 한다.

DEBUG명시 LOG_LEVEL / LOG_CONSOLE_LEVEL기본 console 임계값 결과
false둘 다 미설정INFO·WARNING·ERROR·CRITICAL
true둘 다 미설정DEBUG·INFO·WARNING·ERROR·CRITICAL
falseDEBUG / DEBUGDEBUG도 허용. 앱 DEBUG 모드는 여전히 false
trueWARNING / WARNINGWARNING 이상. startup INFO 차단
어느 값이든INFO / DEBUGroot가 DEBUG 차단. console만 낮춰도 DEBUG 안 나옴
어느 값이든DEBUG / INFOconsole은 INFO 이상만 표시

레벨은 해당 종류 하나만 고르는 스위치가 아니라 최소 심각도이다. 각 명시 레벨은 DEBUG에 따른 기본 계산보다 우선한다. DEBUG 로그 허용과 앱 DEBUG 모드는 별개이다. 필터·개별 로거 상태·큐 포화·출력 실패도 있으므로 레벨 통과만으로 기록 성공을 보장하지 않는다.

6. 로그 출력 대상·ENV·listener의 차이

Default는 모든 환경에서 root의 BoundedQueueHandler를 거쳐 QueueListener 스레드가 stdout에 쓴다. staging/production에는 ERROR 이상 stderr도 추가되어 오류가 양쪽에 보일 수 있다. 앱 파일 핸들러·rotation은 없다. SqlNoiseFilter·ContextFilter는 큐 적재 전에 동작한다.

ENV는 handler 구성·UTC/로컬 타임존·밀리초 형식에, DEBUG는 미설정 레벨 기본값에 사용된다. “production이면 무조건 INFO”라는 주석만 믿으면 명시값을 놓친다. LOG_CONSOLE_ENABLED는 필드로 존재하지만 현재 build_dictconfig의 console 생성 분기에 사용되지 않으므로 false만 지정해 console이 꺼진다고 보장할 수 없다.

Uvicorn 전용 setup_uvicorn_logging은 별도 handler·레벨 구성을 만든다. 앱 root의 LOG_CONSOLE_LEVEL과 동일한 경로라고 가정하지 않는다. 기본 CLI 로그 설정이면 Uvicorn 기본 포맷이 남을 수 있다.

코드 근거: app/utils/logs/config.py · app/utils/logs/setup.py

7. 기능·모델·초기화 hook의 실제 등록 순서

main.py는 home/blog/reply/sns/user/auth/catalog/reports를 import하고 패키지가 공개한 router를 app.include_router(..., prefix="/api")로 명시 취합한다. 기능 __init__.py는 하위 router와 모델을 import하며 home은 register_sink도 import 시 실행한다. sink 등록 자체는 네트워크가 아닌 process-local 연결이다.

iter_model_modules()는 app.features의 패키지 중 models.models 경로를 찾아 정렬하고 import_all_models()가 Base.metadata를 채운다. 라우터 명시 목록과 모델 탐색 목록은 다른 정책이다. main에서 라우터를 빼도 디렉터리가 남으면 모델 탐색·Alembic에 포함될 수 있다.

8. 앱 조립과 DB 객체 준비: 아직 접속 완료는 아니다

FastAPI를 title/version/description/lifespan 및 문서 URL로 생성한다. DEBUG=true일 때만 /openapi.json·Scalar /docs를 활성화한다. CustomCORSMiddleware.configure_cors와 setup_user_info_middleware, 글로벌 예외 handler, 기능 router, /health·/ready를 등록한다. ADMIN은 DEBUG와 독립적이다.

ADMIN=true이면 SQLAdmin이 /admin을 마운트하고 앱별 admin_views를 등록한다. 이는 JSON API response_model과 별도 관리 UI이다. 현재 인증 backend가 없으므로 외부 공개 환경에서는 ADMIN=false를 명시해야 한다. DEBUG=false로 Admin까지 자동 비활성화되지는 않는다.

session.py는 import 시 create_async_engine으로 writer engine, 필요한 read_engines, background_engine과 세션 팩토리를 만든다. 엔진 생성은 URL·pool 정책 준비이며 실제 SELECT 검증이 아니다. pool 연결은 실제 사용 시 확보된다. pool_pre_ping=True도 import 때 모든 DB 검사라는 뜻이 아니다.

객체수명·역할
engine / writer_engine프로세스 공유 writer pool: 요청·DDL·readiness·Admin
read_engines / db_routerreplica pool·writer/reader 바인딩·sticky 정책
AsyncSessionLocal요청별 AsyncSession을 생성하는 공유 팩토리
background_engine / BackgroundSessionLocal접속 로그 등 별도 writer pool·세션 팩토리
AsyncSession요청 또는 한 독립 작업의 트랜잭션 상태. 전역 공유 금지

실제 접속은 engine.begin의 DDL·engine.connect의 readiness·세션 첫 쿼리/flush 등에 필요하다. DEBUG=false로 DDL을 생략하면 Redis가 준비됐을 때 DB 미준비 상태로 기동할 수도 있지만 /ready=503, DB API·접속 로그 저장 실패 가능성이 남는다.

expire_on_commit=False는 commit 뒤 속성 만료를 줄이고 autoflush=False는 SELECT 전 자동 flush를 끈다. session.add는 메모리 등록이라 동기 메서드이며 flush/refresh/execute/commit은 I/O라 await한다.

9. lifespan → 자원 관리 → 개발용 테이블 생성 → yield

@asynccontextmanager는 async generator를 context manager로 만든다. lifespan의 async with manage_application_resources(app): yield는 내부 준비 완료 후 자신도 yield해 ASGI 서버에 시작 준비 완료를 알린다. yield는 서버를 하나 더 만드는 명령이 아니라 context를 요청 처리 기간 동안 열린 상태로 유지하는 경계다. 종료/기동 실패/예외에서는 context exit로 돌아온다. FastAPI lifespan 공식 계약.

실제 구조 발췌 — 로그·시간 측정 생략

resources = ApplicationResources()
app.state.resources = resources
async with _log_queue(), _database(app), _redis(app), _background_tasks():
    await _prepare_database(resources)
    yield resources

ApplicationResources는 model_modules/table_count/tables_created를 보관한다. _database가 이미 import 시 만든 엔진의 정리 책임을 확보하고 _redis는 ping 성공 후 진입을 끝낸다. 모든 context에 들어간 뒤 _prepare_database가 모델을 import하고 metadata 수를 센다. 0개는 DB 접속 생략, 1개 이상+DEBUG=false는 DDL 생략, DEBUG=true는 create_db_tables(import_models=False)이다.

create_db_tables는 writer engine.begin 안에서 connection.run_sync(Base.metadata.create_all)을 실행하며 DDL에는 30초 timeout guard가 있다. create_all은 없는 테이블의 개발용 생성이고 기존 컬럼 변경·삭제·데이터 이동을 처리하는 migration은 아니다. MySQL 데이터베이스 자체와 계정 권한은 미리 준비해야 한다.

코드 근거: app/core/resources.py · manage_application_resources · app/core/db/session.py · create_db_tables · main.py · lifespan

10. Redis 주소가 임의이거나 서버가 없을 때

Redis.from_url은 비동기 client/pool을 구성하고 await client.ping()에서 실제 연결·인증·명령 왕복을 검증한다. socket_connect_timeout과 socket_timeout은 각 5초이다. 성공 후에만 app.state.redis가 client를 참조한다. DEBUG와 무관한 필수 기동 조건이며 현재 disable 설정은 없다.

서버 부재·잘못된 주소/포트·비밀번호는 ConnectionError/AuthenticationError/TimeoutError 등으로 실패할 수 있다. 오류 타입을 ERROR로 기록하고 다시 raise하므로 yield에 도달하지 않고 일반 Uvicorn 실행에서는 application startup failure로 서비스 시작이 중단된다. 최종 traceback 출력·exit code는 실행기와 로그 설정에 따라 별도로 확인한다.

5초를 DNS·retry·모든 startup을 합친 엄격한 전체 상한으로 설명하지 않는다. client aclose는 client pool 정리이며 Redis 서버 종료나 키 삭제가 아니다. ping 성공은 기동 순간 도달 가능성일 뿐 runtime 장애 감시·모든 명령 재시도 보증이 아니다. /ready는 DB만 검사하고 Redis를 재검사하지 않는다.

ping 실패 시점에는 _background_tasks에 아직 진입하지 않았으므로 background drain은 실행되지 않는다. 정리는 Redis aclose → DB dispose(“자원 해제 완료” 로그) → 로그 큐 flush 순이며, app.state.redis·app.state.resources는 None으로 남는다. 회귀 테스트: tests/core/test_resources.py::test_redis_connection_failure_stops_startup_and_cleans_up.

코드 근거: app/core/resources.py · tests/core/test_resources.py · app/celery/app.py

11. 요청마다 반복되는 DI·세션·미들웨어·접속 로그

요청은 middleware 체인을 통과해 method/path에 맞는 endpoint로 간다. UserInfoMiddleware는 활성/제외 경로·확장자를 판정하고 User-Agent/요청 정보를 수집한다. call_next(request)가 downstream 응답을 반환한 뒤 상태·시간을 붙여 access_log_tasks.spawn으로 저장 태스크를 제출한다. 이는 클라이언트가 모든 응답 바이트를 받은 뒤라는 보증이 아니며 call_next가 예외로 끝나는 모든 경로의 로그 보증도 아니다.

Depends 그래프는 세션 generator → 기능 get_*_service → Service → Repository이다. 세션은 generator의 async with 안에 있고 종료 시 close, 전달된 일반 예외에는 rollback 후 재전파를 한다. writer는 처음부터 primary, 조회는 read-only 표시이다. 쓰기 endpoint 본문이 업무 후 await service.commit을 호출하고 성공 응답을 반환한다.

FastAPI의 기본 use_cache=True는 한 요청에서 같은 dependency를 재사용한다. 일부 주석의 “호출마다 새 세션”은 직접 generator 실행과 DI 캐시를 구분해야 한다. 서로 다른 writer/read-only getter, use_cache=False, 직접 함수 호출은 별개다. 요청별 캐시는 전역 AsyncSession 공유와 다르다. FastAPI DI 공식 근거.

HomeAccessLogSink.save는 background_db_session()으로 별도 background 세션을 열고 UserAccessLogService를 조립해 저장·명시 commit한다. 요청 세션을 background에 넘기지 않는다. pool 분리는 CPU/DB 서버/메모리 경쟁 전체를 없애지 않는다.

BackgroundTaskRunner 기본 상한은 256개이다. 초과분은 비핵심 로그를 드롭하고 집계한다. 중요한 업무 저장·결제·발송을 드롭 가능한 이 runner에 넣지 않는다. 종료 drain은 완료를 기다린 후 남은 작업 취소·회수를 시도한다.

13. 종료 순서·시간 예산·보장의 한계

중첩 context 역순은 background → Redis → DB → log queue flush이다. _run_cleanup은 일반 Exception/timeout만 기록·삼키고 CancelledError를 삼키지 않는다. 안쪽 exit에서 예외가 나도 바깥 context exit를 진행하는 구조이다. Redis state는 정리 전 None, resources state는 DB cleanup 경로에서 None으로 지운다. dispose_engine은 모든 엔진 dispose를 gather(return_exceptions=True)로 시도한다.

background 5초 guard에서 완료 대기는 4초로 하여 cancel/gather 여유를 둔다. Redis 5초·DB 10초이며 로그 flush는 queue 모듈의 별도 상수이다. SHUTDOWN_TOTAL_TIMEOUT_SECONDS=20 상수 자체가 전체를 감싼 hard deadline은 아니다. lifespan은 listener를 멈추지 않고 flush만 한다. listener stop은 logging setup의 process exit hook·지원 신호 경로의 책임이다.

자동 cleanup은 Python context exit·정상 ASGI 종료가 진행될 때의 설명이다. SIGKILL·강제 종료·추가 취소·event loop 중단·무응답 I/O에는 완전 회수나 로그 무손실을 보장하지 않는다. dispose는 pool 정리이며 모든 실행 중 세션을 대신 닫거나 엔진 객체를 영구 사용 불가능하게 만드는 API가 아니다. DB 사용 주체를 먼저 정리한다.

14. API lifespan 밖: Celery·Alembic

FastAPI 실행은 Celery worker/beat를 자동 시작하지 않는다. app/celery/app.py는 같은 Redis URL을 broker/backend로 사용하고 중앙 tasks.py를 포함한다. run_async는 동기 worker 안에서 프로세스별 영속 loop를 재사용한다. API lifespan이 worker의 broker 연결·loop를 대신 정리하지 않는다.

이 저장소의 worker shutdown은 살아 있는 worker loop에서 dispose_engine을 CELERY_CLEANUP_TIMEOUT_SECONDS=10.0 안에서 실행하고 shutdown_asyncgens → loop.close → 전역 loop 참조 해제 순이다. prefork 자식 초기화의 restart_log_listener 경로도 있다.

migrations/env.py는 db_settings.ALEMBIC_URL을 사용하고 Base.metadata를 target_metadata로 설정한다. import_all_models로 디렉터리 모델을 탐색한다. Alembic은 FastAPI lifespan에 진입하지 않으므로 startup Redis ping은 실행하지 않는다.

online migration은 실제 writer 접속이 필요하다. 서버 기동이 자동 upgrade를 수행하지 않으며 DEBUG=false 전환 전에 스키마 migration을 적용한다. 생성 후보는 사람이 검토한다.

코드 근거: app/celery/lifecycle.py · app/celery/task.py · run_async · app/celery/app.py · migrations/env.py

15. 실행·장애 확인과 검증 경계

  • 저장소 루트에서 실행한다. 프로세스 환경변수가 .env를 덮어쓰는지 확인한다. .env.example은 기존 .env가 없을 때만 복사한다.
  • Redis 미준비 호스트에서는 실패가 예상된다. DEBUG=false는 Redis 검증을 끄지 않는다.
  • development/test에서 DB 없이 기동 구조만 볼 경우 DEBUG=false·ADMIN=false·ACCESS_LOG_ENABLED=false를 검토한다. Redis는 필요하고 /ready=503은 DB 미준비 상태에 맞는 결과다.
  • DEBUG=true DDL은 DB 생성·계정 권한·기존 컬럼 변경을 대신하지 않는다. ADMIN=true는 인증 없는 UI다.
  • startup INFO가 안 보이면 DEBUG 표시 인자가 아니라 LOG_LEVEL·LOG_CONSOLE_LEVEL·handler/filter·configure 경로를 추적한다.
  • 404는 파일 존재가 아니라 설치 규칙과 prefix 합성을 먼저 점검한다. 종료 성공 로그만으로 데이터 무손실을 단정하지 않는다.
