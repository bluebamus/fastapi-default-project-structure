1. 개요와 범위 — 두 인증 체계

이 저장소에는 인증 체계가 둘 있다. 서로 다른 경로에 붙고, 서로를 대신하지 않는다.

  • API 인증 — OAuth2 password flow 로 받은 JWT Bearer 토큰. /api/v1/... 의 보호 경로가 Authorization: Bearer 헤더만 본다(app/core/security/dependencies.py:38 oauth2_scheme, :68 get_current_principal). 어느 API 뷰가 보호되는지는 뷰마다 선언한 접근 수준(Public·PublicWrite·LoginRequired·SuperuserRequired)이 정하고, 선언이 빠진 뷰가 하나라도 있으면 서버가 기동하지 않는다(app/core/security/access.py AccessPolicyGuard).
  • 관리 화면 인증 — /admin 에 마운트된 SQLAdmin 하위 앱 안에서만 동작하는 서명 세션 쿠키 admin_session. 로그인·세션 확인·로그아웃은 AdminAuthBackend(app/features/auth/admin_backend.py:54)가 한다.
확인 결과 — 세션은 /admin 전용이다. 앱 전역 SessionMiddleware 는 없고(메인 앱 user_middleware 에 없음), 세션 미들웨어는 SQLAdmin 이 AuthenticationBackend.middlewares 로 받아 자기 하위 Starlette 앱에만 붙인다. 코드에서 request.session 을 쓰는 곳은 app/features/auth/admin_backend.py 하나다. API 경로는 유효한 admin_session 쿠키를 보내도 401 이다. 설정 SESSION_COOKIE_NAME 은 접속 로그 미들웨어가 그 쿠키 값을 기록용으로 읽을 뿐 (app/core/middlewares/user_info_middleware.py:58·:175) 인증에 쓰지 않는다.

이 사실은 테스트로 고정돼 있다 — tests/test_admin_session_scope.py 의 test_main_app_has_no_session_middleware, test_session_middleware_lives_only_in_the_admin_sub_app, test_api_is_not_authenticated_by_a_valid_admin_session_cookie, test_admin_session_cookie_is_never_set_outside_admin.

2. 구성도와 주입 관계

메인 FastAPI 앱의 미들웨어(CORS·접속 로그)와 API 라우터는 JWT 의존성만 쓴다. SQLAdmin 은 Admin(app, ...) 이 생성되는 순간 /admin 에 별도의 Starlette 하위 앱으로 마운트되고, 세션 미들웨어는 그 하위 앱 안에만 있다.

Redis 는 바깥 앱의 lifespan 이 연 app.state.redis 를 쓴다. SQLAdmin 하위 앱에서는 request.app 이 하위 앱을 가리켜 get_redis(request) 로는 닿지 않으므로, 조립 함수가 바깥 앱을 클로저로 잡는다(app/features/admin.py:114 _app_redis). 비밀번호 확인·bcrypt→Argon2 재해시는 API 로그인과 같은 AuthService.authenticate(app/features/auth/services/auth_service.py:65)를 그대로 쓴다 — 관리 화면용 검증 코드를 따로 두지 않는다.

코드 근거: app/features/admin.py · build_admin_auth_backend · app/features/admin.py · create_admin_interface · app/features/auth/services/auth_service.py · authenticate

3. 기동 결정 흐름

예전 이름 ADMIN(true=켬)은 뜻이 뒤집힌 ADMIN_DISABLED(true=끔)로 바뀌었다. 조용히 무시하면 ADMIN=false 로 꺼 두었던 배포가 관리 화면이 켜진 채 뜨므로, 남아 있으면 기동을 멈춘다(config.py:1234, 대소문자 무시, ENV=test 는 검사하지 않는다). ADMIN_DISABLED=true 면 main.py:325 의 분기가 app.features.admin 을 import 하지 않아 sqladmin·인증 백엔드·세션 미들웨어가 생성되지 않고, 앱의 어떤 응답·기동 로그에도 관리 화면 경로가 나오지 않는다(tests/test_admin_disabled.py).

코드 근거: config.py · validate_no_legacy_admin · main.py · tests/test_admin_disabled.py

4. 로그인 시퀀스

  1. 폼 값은 username·password(API 로그인과 같은 식별자). IP 는 ClientIPResolver 가 TRUSTED_PROXY_HOPS 로 정한다(admin_backend.py:95-98).
  2. 레이트 리밋은 API 와 같은 한도(AUTH_LOGIN_MAX_ATTEMPTS·AUTH_LOGIN_IP_MAX_ATTEMPTS·AUTH_LOGIN_WINDOW_SECONDS)를 쓰되 키 접두사가 admin:rl:login 이다(:101-110). 맞는 비밀번호여도 한도가 먼저다.
  3. 자격 확인은 AuthService.authenticate(:118-123). 없는 사용자·틀린 비밀번호·비활성은 같은 예외로 온다. 일반 사용자도 같은 실패로 합친다(:125).
  4. 성공하면 IP+사용자명 카운터만 지우고(IP 카운터는 남긴다), 세션을 비운 뒤 user_id 하나만 넣는다(:133-136) — 세션 고정 방지.

코드 근거: app/features/auth/admin_backend.py · login · app/core/security/rate_limit.py · RateLimiter · app/core/security/password_hasher.py · verify_and_update

5. 요청별 인증 흐름

서명·만료 검증은 starlette SessionMiddleware 가(실패하면 조용히 빈 세션), 사용자 확인은 AdminAuthBackend.authenticate (admin_backend.py:140-149)가 한다. SQLAdmin 의 login_required 가 모든 관리 라우트에서 이 메서드를 부른다. DB 를 매 요청 확인하므로 강등·비활성화·삭제가 다음 요청부터 반영된다 — JWT 의 R-014 와 다르다.

코드 근거: app/features/auth/admin_backend.py · authenticate

7. 로그아웃 흐름

서버에 세션 저장소가 없으므로 로그아웃은 "쿠키를 비운 새 쿠키로 덮어쓰기" 다. 로그아웃 전에 복사해 둔 쿠키 문자열은 서명이 유효한 동안(최대 8시간) 다시 쓸 수 있다 — 다만 요청마다 DB 확인을 하므로 그 사이 계정을 강등·비활성화하면 즉시 막힌다(보안 설계).

남은 위험

  • 서버 쪽 세션 폐기 목록이 없다 — 로그아웃 전에 복사된 쿠키는 만료(8시간)까지 서명이 유효하다. 계정이 슈퍼유저·활성인 동안에만 쓸 수 있다(admin-login R-001).
  • 로그인 폼 자체에는 CSRF 토큰이 없다(로그인 CSRF — 공격자 계정으로 로그인시키기). 공격자도 슈퍼유저여야 의미가 있어 수용했다(admin-login R-002).
  • 고정 창 레이트 리밋의 창 경계 2배 버스트·분산 IP 공격은 API 로그인과 같다(service-hardening R-004·R-007).
  • 로그인 화면의 Bootstrap CSS 는 CDN(jsDelivr)에서 받는다 — CDN 이 막힌 망에서는 스타일 없이 보인다(기능은 동작). SRI 가 내용 변조를 막는다.

배포 체크리스트 (관리 화면)

  1. 관리 화면을 쓰지 않으면 ADMIN_DISABLED=true.
  2. 예전 ADMIN 설정을 환경 변수·.env 에서 지웠다(남아 있으면 기동 거부).
  3. SESSION_SECRET_KEY 를 새로 만들었다: uv run python -c "import secrets; print(secrets.token_urlsafe(48))".
  4. 첫 슈퍼유저를 scripts/create_superuser.py 로 만들었다.
  5. HTTPS 로 접속한다(배포 환경 쿠키는 Secure). 프록시 뒤면 TRUSTED_PROXY_HOPS 를 설정했다.

키 교체 영향: SESSION_SECRET_KEY 를 바꾸면 모든 관리 세션이 무효가 된다(다시 로그인). API 토큰에는 영향이 없다.

12. 확장 시 주의

  • 새 관리 뷰 — 기능 폴더의 admin.py 에 ModelView 와 admin_views 를 만들고 app/features/admin.py 의 ADMIN_VIEWS 에 한 줄 더한다. 인증은 SQLAdmin 이 모든 관리 라우트에 이미 걸어 준다 — 뷰마다 따로 할 일이 없다. 기능 패키지 __init__.py 로 재노출하지 않는다(ADMIN_DISABLED=true 에서 sqladmin 이 로드되지 않게).
  • 필터 — column_filters 에는 sqladmin.filters 객체(BooleanFilter·OperationColumnFilter 등)를 넣는다. 모델 컬럼을 그대로 넣으면 sqladmin 0.32 의 목록 화면이 parameter_name AttributeError 로 500 이다. 생성 시각(UTCDateTime)에는 연산 필터를 걸지 않는다 — 날짜 형으로 인식되지 않아 입력 문자열이 그대로 바인딩된다(500). tests/test_admin_views_render.py 가 모든 뷰의 목록·필터·상세 화면을 로그인한 슈퍼유저로 200 인지 확인한다(admin-login F-005).
  • 로그인 화면 — app/templates/admin/sqladmin/login.html 이 SQLAdmin 기본 화면을 덮어쓴다(templates_dir 의 FileSystemLoader 가 패키지 템플릿보다 먼저 찾아진다). 이 화면과 연동은 유지 대상이다 — 바꿀 때 지킬 것: form action url_for('admin:login')·POST, 필드 이름 username·password, error 변수의 자동 이스케이프, Bootstrap 버전을 올리면 SRI 해시를 실제 파일로 다시 계산. tests/test_admin_login.py 의 화면 테스트가 이것을 지킨다.
  • API 에 세션 인증을 섞지 않는다 — API 는 상태 없는 Bearer 토큰이 계약이다. 쿠키 인증을 API 에 더하면 CSRF 방어가 필요해지고 (지금은 헤더라 불필요), 두 체계의 폐기·수명이 엇갈린다. 관리 세션 미들웨어를 메인 앱으로 옮기지 말 것 — tests/test_admin_session_scope.py 가 막는다.
  • 세션에 더 많은 값을 넣지 않는다 — 서명일 뿐 암호화가 아니고, 권한은 요청마다 DB 에서 읽는 것이 설계다.
