/admin 인증: 슈퍼유저 로그인 · Redis 서버 세션 · CSRF · ADMIN_DISABLED

SQLAdmin 관리 화면의 로그인과 세션이 어떻게 조립되고, 요청마다 무엇을 확인하며, 상태를 바꾸는 요청을 어떻게 CSRF 로부터 지키고, API 인증(JWT)과 어디서 갈라지는지 코드 기준으로 설명한다. 이 주제의 원본 문서다 — 코드와 다르면 코드가 정답이며 이 문서를 고친다. 설계 결정의 근거는 CRP 그룹 admin-login·security-ops-hardening·admin-session-hardening 에 있다.

1. 개요와 범위 — 두 인증 체계

이 저장소에는 인증 체계가 둘 있다. 서로 다른 경로에 붙고, 서로를 대신하지 않는다.

  • API 인증 — OAuth2 password flow 로 받은 JWT Bearer 토큰. /api/v1/... 의 보호 경로가 Authorization: Bearer 헤더만 본다(app/core/security/dependencies.py 의 oauth2_scheme·get_current_principal). 어느 API 뷰가 보호되는지는 뷰마다 선언한 접근 수준(Public·PublicWrite·LoginRequired·SuperuserRequired)이 정하고, 선언이 빠진 뷰가 하나라도 있으면 서버가 기동하지 않는다(app/core/security/access.py AccessPolicyGuard).
  • 관리 화면 인증 — /admin 에 마운트된 SQLAdmin 하위 앱 안에서만 동작하는 Redis 서버 세션. 쿠키 admin_session 에는 무작위 세션 ID 만 있고 내용은 Redis 에 있다(app/core/security/admin_session.py). 로그인·세션 확인·로그아웃은 AdminAuthBackend(app/features/auth/admin_backend.py), 상태를 바꾸는 모든 요청의 CSRF 검사는 AdminCsrfMiddleware 가 한다.
2026-10-19 변경 (admin-session-hardening). 관리 세션이 서명 쿠키(starlette SessionMiddleware, 내용 전체가 쿠키)에서 Redis 서버 세션으로 바뀌었다 — 로그아웃·강등·비활성화·삭제가 서버에서 즉시 세션을 지우고, 로그아웃 전에 복사해 둔 쿠키는 더 쓸 수 없다. 로그인 이후의 생성·수정·삭제·로그아웃도 CSRF 토큰을 요구하고, 로그아웃은 POST 만 받는다. 결정 근거: admin-session-hardening design-baseline.
세션은 /admin 전용이다. 앱 전역 세션 미들웨어는 없고, RedisSessionMiddleware·AdminCsrfMiddleware 는 SQLAdmin 이 AuthenticationBackend.middlewares 로 받아 자기 하위 Starlette 앱에만 붙인다. API 경로는 admin_session 쿠키를 보내도 401 이다. 설정 SESSION_COOKIE_NAME 은 접속 로그 미들웨어가 그 쿠키 값을 기록용으로 읽을 뿐 (app/core/middlewares/user_info_middleware.py) 인증에 쓰지 않는다. 테스트: tests/test_admin_session_scope.py.

2. 구성도와 주입 관계

메인 FastAPI 앱의 미들웨어(CORS·접속 로그)와 API 라우터는 JWT 의존성만 쓴다. SQLAdmin 은 Admin(app, ...) 이 생성되는 순간 /admin 에 별도의 Starlette 하위 앱으로 마운트되고, 세션·CSRF 미들웨어는 그 하위 앱 안에만 있다. 순서는 세션이 바깥, CSRF 가 안쪽이다 — CSRF 는 세션의 토큰을 읽는다.

Redis 는 바깥 앱의 lifespan 이 연 app.state.redis 다. SQLAdmin 하위 앱에서는 request.app 이 하위 앱을 가리켜 get_redis(request) 로는 닿지 않으므로 조립 함수가 바깥 앱을 클로저로 잡고(app/features/admin.py 의 _app_redis), 세션 저장소는 요청마다 그 Redis 로 만든다(미들웨어가 앱 조립 시점에 만들어지지만 Redis 는 lifespan 이 연 뒤에야 있다). 비밀번호 확인·bcrypt→Argon2 재해시는 API 로그인과 같은 AuthService.authenticate 를 그대로 쓴다.

코드 근거: app/features/admin.py · build_admin_auth_backend · app/features/admin.py · create_admin_interface · app/core/security/dependencies.py · new_admin_session_store

만료 정책

  • 절대 만료 — created_at(로그인해 세션을 만든 시각) + ADMIN_SESSION_MAX_AGE_SECONDS. 요청해도 연장되지 않는다. 지나면 읽을 때 키를 지우고 빈 세션으로 본다(AdminSessionStore.load).
  • 미사용 만료 — 요청마다 TTL 을 ADMIN_SESSION_IDLE_SECONDS 로 다시 잡는다. 단 절대 만료까지 남은 시간보다 길게 잡지 않는다 (AdminSessionStore.save). 설정은 둘 다 60 이상, 미사용 ≤ 절대(어기면 기동 시 ValidationError).
  • 되살리기 방지 — 기존 세션 저장은 SET ... XX(키가 있을 때만)다. 요청을 처리하는 도중 다른 곳에서 폐기된 세션을 그 요청의 응답 저장이 다시 만들지 않는다. 새 세션은 SET ... NX.
  • 세션 고정 방지 — 로그인 성공은 session.clear() 후 rotate_session(request) 로 미들웨어에 회전을 요청한다 → 새 sid 발급, 이전 키 삭제, 사용자 인덱스에서도 제거. CSRF 토큰도 함께 버려져 새로 만들어진다.

4. 기동 결정 흐름

ADMIN_DISABLED=true 면 main.py 의 분기가 app.features.admin 을 import 하지 않아 sqladmin·인증 백엔드·미들웨어가 생성되지 않는다. API 의 사용자 비활성화·삭제가 쓰는 폐기 provider get_admin_session_store 도 이때는 None 을 돌려준다(관리 세션이 없다). 앱의 어떤 응답·기동 로그에도 관리 화면 경로가 나오지 않는다(tests/test_admin_disabled.py).

코드 근거: config.py · SessionSettings · main.py · tests/test_admin_disabled.py

5. 로그인 시퀀스

  1. 폼 값은 username·password(API 로그인과 같은 식별자). IP 는 ClientIPResolver 가 TRUSTED_PROXY_HOPS 로 정한다.
  2. CSRF 가 먼저다 — AdminCsrfMiddleware 가 엔드포인트보다 먼저 폼의 csrf_token 을 세션 값과 대조한다. 다르면 로그인 화면을 403 으로 다시 그리고(AdminAuthBackend.csrf_rejected) 레이트 리밋 카운터도 자격 확인도 건드리지 않는다 — 위조 요청이 피해자의 시도 한도를 깎지 못한다. 2026-10-19 부터 이 검사는 백엔드의 login 이 아니라 미들웨어 한 곳에서 한다(중복 검사 없음).
  3. 레이트 리밋은 API 와 같은 한도를 쓰되 키 접두사가 admin:rl:login 이다. 맞는 비밀번호여도 한도가 먼저다.
  4. 자격 확인은 AuthService.authenticate. 없는 사용자·틀린 비밀번호·비활성·일반 사용자는 같은 400 으로 합친다.
  5. 성공하면 IP+사용자명 카운터만 지우고, 세션을 비운 뒤 user_id 하나만 넣고 세션 ID 를 회전한다.

코드 근거: app/features/auth/admin_backend.py · login · app/core/security/admin_session.py · AdminCsrfMiddleware · app/core/security/admin_session.py · rotate_session

6. 요청별 인증 흐름

세션 복원·저장은 RedisSessionMiddleware, 토큰 대조는 AdminCsrfMiddleware, 사용자 확인은 AdminAuthBackend.authenticate 가 한다. SQLAdmin 의 login_required 가 모든 관리 라우트에서 authenticate 를 부른다. DB 를 매 요청 확인하는 것은 서버 쪽 폐기(폐기 흐름)와 이중 방어다 — 관리 화면 밖에서 DB 를 직접 고쳐도 다음 요청에서 막힌다.

코드 근거: app/core/security/admin_session.py · RedisSessionMiddleware · app/features/auth/admin_backend.py · authenticate

7. CSRF 흐름 — meta · 스크립트 · 미들웨어

sqladmin 0.32 가 그리는 화면과 statics/js/main.js 를 조사해 상태를 바꾸는 요청을 모두 목록화했다. 서버는 경로와 상관없이 /admin 아래의 POST·PUT·PATCH·DELETE 전부를 검사하고, 클라이언트는 덮어쓴 base.html 하나가 토큰을 싣는다.

요청메서드·경로보내는 방식토큰을 싣는 방법

사용자 정의 actionGET /admin/{identity}/action/{slug}window.location등록된 것이 없다 — GET 이라 미들웨어가 보지 않으므로 쓰지 않는다(test_no_view_registers_a_custom_get_action)
로그아웃POST /admin/logout(원래 GET)layout.html 의 링크라우트를 POST 전용으로 교체(GET 은 405), 스크립트가 링크 클릭을 토큰 실은 POST 폼으로
내보내기·상세·목록·ajax lookup·파일 내려받기GET링크·select2상태를 바꾸지 않는다 — 대상 아님
  • 토큰 — 세션에 하나(csrf_token, secrets.token_urlsafe(32)). 화면을 그릴 때 템플릿 전역 csrf_token(request) 가 없으면 만든다. 로그인 때 세션과 함께 회전한다. 세션이 없으면(토큰이 없으면) 본문을 읽지도 않고 거부한다.
  • 본문 처리 — 헤더가 없고 폼(application/x-www-form-urlencoded·multipart/form-data)이면 본문을 끝까지 버퍼링해(상한 10 MiB, 넘으면 413) Starlette 폼 파서로 읽고, 같은 바이트를 다운스트림 receive 로 다시 흘린다 — sqladmin 이 같은 폼을 다시 읽는다. 헤더로만 통일하지 않은 이유: 생성·수정은 브라우저 네이티브 폼 제출이라 헤더를 붙일 수 없다(admin-session-hardening ADR-003).
  • 덮어쓴 템플릿 — app/templates/admin/sqladmin/base.html 은 원본을 복사하지 않고 sqladmin_original/base.html(sqladmin 이 제공하는 접두사 로더)을 확장해 head_meta·tail 두 블록에만 super() + 추가를 한다. sqladmin 을 올릴 때 원본 블록·로그아웃 링크가 바뀌면 tests/test_admin_csrf.py 의 드리프트 검사가 실패한다.
  • 로그아웃 — sqladmin 의 로그아웃 라우트는 GET 만 받는다. _logout_post_only 가 같은 엔드포인트의 POST 전용 라우트로 바꿔 끼운다. 다른 사이트가 <img src="/admin/logout"> 로 강제 로그아웃시킬 수 없다(GET 은 405).

남은 위험

  • JS 를 끈 브라우저는 생성·수정·삭제·로그아웃이 403/405 다 — 토큰을 붙이는 것이 인라인 스크립트다(sqladmin 삭제 모달도 원래 JS 가 필요하다).
  • sqladmin @action(GET 으로 상태 변경)은 미들웨어가 보지 않는다 — 쓰지 않는 것으로 막는다(테스트). 필요해지면 action 을 POST 로 감싸야 한다.
  • 세션이 Redis 에만 있어 Redis 를 비우거나(FLUSHDB) 장애가 나면 모든 관리자가 다시 로그인해야 한다(장애 중에는 503).
  • 고정 창 레이트 리밋의 창 경계 2배 버스트·분산 IP 공격은 API 로그인과 같다(service-hardening R-004·R-007).

배포 체크리스트 (관리 화면)

  1. 관리 화면을 쓰지 않으면 ADMIN_DISABLED=true.
  2. 예전 ADMIN 설정을 지웠다(남아 있으면 기동 거부).
  3. SESSION_SECRET_KEY 를 새로 만들었다: uv run python -c "import secrets; print(secrets.token_urlsafe(48))".
  4. Redis(6.2 이상)가 준비됐다 — 관리 세션도 여기 있다.
  5. 첫 슈퍼유저를 scripts/create_superuser.py 로 만들었다.
  6. HTTPS 로 접속한다(배포 환경 쿠키는 Secure). 프록시 뒤면 TRUSTED_PROXY_HOPS 를 설정했다.

키 교체 영향: SESSION_SECRET_KEY 를 바꾸면 같은 쿠키가 다른 Redis 키를 가리켜 모든 관리 세션이 무효가 된다(다시 로그인). 옛 키의 세션은 Redis 에 남았다가 미사용 만료로 사라진다. API 토큰에는 영향이 없다.

14. 확장 시 주의

  • 새 관리 뷰 — 기능 폴더의 admin.py 에 ModelView 와 admin_views 를 만들고 app/features/admin.py 의 ADMIN_VIEWS 에 한 줄 더한다. 인증·CSRF 는 하위 앱 전체에 이미 걸려 있다 — 뷰마다 할 일이 없다.
  • sqladmin @action 을 쓰지 않는다 — GET 으로 상태를 바꿔 CSRF 미들웨어를 비켜 간다. tests/test_admin_csrf.py 가 막는다.
  • 새 상태 변경 요청 — POST·PUT·PATCH·DELETE 면 자동으로 검사된다. 직접 쓰는 JS 는 같은 출처 fetch/XHR 이면 스크립트가 헤더를 붙이고, 네이티브 POST 폼은 submit 때 hidden 필드가 붙는다. form.submit() 처럼 submit 이벤트가 없는 제출은 직접 csrf_token 필드를 넣는다.
  • 템플릿 — base.html 은 원본을 확장만 한다. 다른 원본 템플릿을 덮어써야 하면 같은 방식(sqladmin_original/ 확장)을 쓰고 드리프트 테스트를 더한다. 로그인 화면(app/templates/admin/sqladmin/login.html)의 hidden csrf_token 은 지우지 않는다.
  • 필터 — 생성 시각은 LocalDateFilter(같은 날·이후·이전·기간). sqladmin 연산 필터를 UTCDateTime 에 걸지 않는다.
  • 비밀번호 변경 경로를 만들면 refresh revoke_user 와 관리 세션 revoke_user 를 함께 부른다.
  • API 에 세션 인증을 섞지 않는다 — 세션 미들웨어를 메인 앱으로 옮기지 말 것(tests/test_admin_session_scope.py).
