3. 세션과 의존성 선택

개발·확장의 세부 주제입니다. 목적·책임·운영 및 확장 시 지켜야 할 계약을 설명합니다.

3. 세션과 의존성 선택

유스케이스가 쓰기인가 / 조회 후 쓰기인가 / 잠금이 필요한가?
  ├─ 예  → get_writer_db_session → 같은 세션으로 작업 → View 에서 응답 전 커밋 1회
  └─ 아니오 → 복제 지연을 허용하는가?
        ├─ 예  → get_read_only_db_session → 커밋 없음
        └─ 아니오 → get_writer_db_session 으로 조회만 (커밋 없음)

HTTP 메서드 이름이 아니라 하는 일이 세션을 정합니다. Raw SQL 이라고 쓰기 세션을 쓰지 않고, 조회 후 쓰기의 첫 SELECT 가 replica 로 새지 않도록 writer 를 씁니다. 이름 규칙과 동작은 ARCHITECTURE §4.2.

# app/features/catalog/dependencies/catalog_dependencies.py
async def get_catalog_service(
    db_session: AsyncSession = Depends(get_writer_db_session),
) -> CatalogService:
    return CatalogService(db_session)


async def get_catalog_service_readonly(
    db_session: AsyncSession = Depends(get_read_only_db_session),
) -> CatalogService:
    return CatalogService(db_session)
  • 인자·속성 이름은 db_session/self.db_session 입니다.
  • 한 요청에서 여러 Service 가 하나의 원자적 쓰기에 참여하면 같은 writer 세션을 넘기고, 커밋 주체는 View 하나로 둡니다. Service 를 전역 싱글턴으로 두지 않습니다(세션이 요청을 넘나듭니다).
  • 읽기 세션의 쓰기 차단은 DB_ROUTER_ENABLED 와 무관하게 동작합니다(기본값 false 포함). 그래도 쓰기는 처음부터 writer 의존성으로 고정하고, 운영에서는 DB 권한(읽기 전용 계정)을 함께 씁니다 — session.info 표시는 보안 경계가 아닙니다.
  • 장기 자원(예: Redis client)이 필요하면 모듈 전역을 새로 만들지 말고 app/core/resources.py 에 자원 컨텍스트를 추가하고 app.state 에서 꺼내는 작은 의존성을 둡니다. Redis 는 app/core/redis.py 의 get_redis 가 그 의존성입니다(서버 최소 버전 REDIS_MIN_VERSION 도 거기 — 6.2 를 넘는 명령을 새로 쓰면 올린다) — redis: Redis = Depends(get_redis) 로 받고, 테스트는 app.dependency_overrides[get_redis] 로 fakeredis(fakeredis.FakeAsyncRedis(), dev 의존성)를 넣습니다 — Redis 를 쓰는 클래스(예: app/core/security/ 의 RefreshTokenStore·RateLimiter)는 가짜 인터페이스 없이 실물 그대로 시험됩니다. 새 자원은 정리 순서(자원을 쓰는 주체 → 자원)와 개별 timeout 을 함께 정합니다.

3.1 라우트 보호 — Principal 주입

인증·인가는 의존성으로만 겁니다(핸들러 본문이 토큰을 파싱하지 않는다). 부품은 전부 core 의 app/core/security/access.py(접근 수준)·app/core/security/dependencies.py(provider·주체)에 있어 어느 기능이든 core 만 import 합니다(기능끼리 import 금지).

모든 뷰는 접근 수준을 하나 선언합니다 — 선언하지 않으면 서버가 기동하지 않습니다(AccessPolicyGuard, ARCHITECTURE §11.2).

요구 쓰는 것 실패
누구나 조회 데코레이터 dependencies=[Public] (GET·HEAD·OPTIONS 만) —
누구나 쓰기(가입·로그인처럼 의도적으로) 데코레이터 dependencies=[PublicWrite] (쓰기 메서드만) —
로그인한 사용자 핸들러 인자 principal: CurrentPrincipal (주체가 필요 없으면 dependencies=[LoginRequired]) 토큰 없음·만료·위조 401
슈퍼유저만 데코레이터 dependencies=[SuperuserRequired] (주체가 필요하면 인자 principal: SuperuserPrincipal) 401 / 403
기능 전체를 슈퍼유저로 뷰마다 dependencies=[SuperuserRequired] — 라우터 단위 APIRouter(dependencies=[SuperuserRequired]) 도 판정상 인정되지만 예시는 뷰 단위로 통일한다. 401/403 문서는 APIRouter(responses=FORBIDDEN_RESPONSES) 401 / 403
소유자 또는 슈퍼유저 Service 가 생성자로 OwnershipPolicy 를 받고 메서드가 principal 을 받아 ensure_can_modify(owner_id, principal) 403
DB 의 사용자 엔티티 auth 의 get_current_user(/me 전용 — 비활성·삭제 사용자 401) 401

Principal(id, username, is_superuser) 은 access 토큰의 sub·username·su 로만 만듭니다 — DB 를 보지 않습니다. 인증에 성공하면 request.state.user_id 가 채워져 접속 로그에 사용자 ID 가 남습니다.

# dependencies — 정책은 provider 로 받아 생성자로 넘긴다
async def get_inventory_service(
    db_session: AsyncSession = Depends(get_writer_db_session),
    ownership: OwnershipPolicy = Depends(get_ownership_policy),
) -> InventoryService:
    return InventoryService(db_session, ownership)

# service — 작성자는 요청 본문이 아니라 주체에서, 수정은 정책 확인 뒤에
async def create_item(self, data: ItemCreate, principal: Principal) -> Item:
    return await self.repository.create({**data.model_dump(), "author_id": principal.id})

async def update_item(self, item_id: str, data: ItemUpdate, principal: Principal) -> Item:
    existing = await self.get_item(item_id)          # 없으면 404 가 먼저
    self.ownership.ensure_can_modify(existing.author_id, principal)
    ...

# view
@router.patch("/items/{item_id}", responses={**_NOT_FOUND, **FORBIDDEN_RESPONSES}, ...)
async def update_item(
    payload: ItemUpdate,
    principal: CurrentPrincipal,
    item_id: str = Path(...),
    service: InventoryService = Depends(get_inventory_service),
) -> ItemResponse: ...
  • 작성자·소유자 필드(author_id 등)는 Create·Update 스키마에 두지 않습니다 — 응답 스키마에만 둡니다.
  • 문서용 UNAUTHORIZED_RESPONSES(401)·FORBIDDEN_RESPONSES(401+403)를 responses= 에 펼쳐 OpenAPI 에 싣습니다.
  • 테스트는 의존성을 바꾸지 않고 tests/auth_headers.py 의 bearer(principal) 로 진짜 토큰을 싣습니다. 기존 CRUD 테스트는 클라이언트 기본 헤더로 bearer()(슈퍼유저)를 씁니다.
# 뷰마다 접근 수준을 하나 — app/core/security/access.py
from app.core.security.access import Public, PublicWrite, SuperuserRequired

@router.get("/items", response_model=ItemListResponse, dependencies=[Public])          # 공개 조회
async def list_items(...) -> ItemListResponse: ...

@router.post("/items", response_model=ItemResponse, status_code=201)                   # 로그인 — 인자가 선언이다
async def create_item(payload: ItemCreate, principal: CurrentPrincipal, ...) -> ItemResponse: ...

@router.delete("/items/{item_id}", status_code=204, dependencies=[SuperuserRequired])  # 슈퍼유저
async def delete_item(item_id: str, ...) -> None: ...

@router.post("/webhooks/payment", dependencies=[PublicWrite])                          # 인증 없는 쓰기 — 의도를 남긴다
async def payment_webhook(...) -> None: ...
  • 선언이 없거나(AccessPolicyError: GET /api/v1/inventory/items: 접근 수준 선언 없음), 수준을 둘 적었거나, 쓰기에 Public·조회에 PublicWrite 를 달면 서버가 기동하지 않습니다. 위반은 전부 한 번에 나옵니다.
  • 새 라우트의 기대 수준을 tests/test_authorization.py 의 EXPECTED_ACCESS 에 더합니다 — 401/403 실요청 테스트가 이 표에서 대상을 뽑습니다.

왜 함수를 감싸는 데코레이터(@login_required)를 만들지 않나. FastAPI 는 핸들러 시그니처를 읽어 의존성 주입·요청 검증·OpenAPI 를 만듭니다. 함수를 감싸면 시그니처가 *args, **kwargs 로 가려져 주입·검증이 깨지고, functools.wraps 로 겉모양을 복사해도 인증 인자를 더하려면 시그니처를 손으로 고쳐야 하며 OpenAPI 의 security 표시도 그 손질에 달립니다. 경로 데코레이터의 dependencies=[...] 가 FastAPI 에서 "데코레이터로 거는" 방법이고, 데코레이터만으로는 생기지 않는 기본 정책(선언 누락 차단)은 기동 검사가 맡습니다.
