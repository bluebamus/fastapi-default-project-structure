새 기능 등록 — 손댈 곳

  1. app/features/<name> 에 기존 기능(catalog: ORM, reports: Raw SQL)과 같은 구조를 만듭니다. 기능명이 URL 세그먼트(/api/v1/<name>/…)가 됩니다.
  2. 뷰마다 dependencies=[Public|PublicWrite|LoginRequired|SuperuserRequired] 중 하나를 선언하거나 principal: CurrentPrincipal/SuperuserPrincipal 인자로 받습니다. 선언이 없으면 기동이 거부됩니다.
  3. 쓰기 핸들러는 응답 DTO 를 검증한 뒤 await service.commit() 을 한 번 부릅니다.
  4. main.py 에 from app.features import … 와 app.include_router(<name>.router, prefix="/api") 를 AccessPolicyGuard().verify(app) 위에 한 줄 추가합니다.
  5. 관리 화면이 필요하면 기능 admin.py 에 admin_views 를 만들고 app/features/admin.py 의 import 와 ADMIN_VIEWS 에 한 줄씩 더합니다.
  6. 모델(models/models.py)과 Celery 태스크(tasks.py)는 자동 탐색되므로 등록할 곳이 없습니다. 모델 변경은 Alembic revision 을 만들고 검토합니다.
  7. app/core/tags_metadata.py, tests/test_route_inventory.py, tests/test_authorization.py 의 EXPECTED_ACCESS, E2E SPECS, README API 표, API 레퍼런스 를 함께 갱신합니다.

파일별 표와 실패 시 증상은 DEVELOPMENT §2.2 가 정본입니다.

코드 리뷰 기준

  • 업무 규칙이 View·Repository 로 새지 않았는가. View 가 SQL·세션을 직접 다루지 않는가.
  • 커밋은 쓰기 핸들러의 service.commit() 한 번뿐이고 DTO 검증 뒤인가. Repository·Dependency 가 커밋하지 않는가.
  • 조회는 read_only 세션, 쓰기·조회 후 쓰기는 writer 세션인가.
  • 다른 기능을 import 하지 않았는가(auth→user 만 허용).
  • 인증 실패 401, 권한 실패 403, 없음 404, 중복 409 를 공통 오류 형식으로 내는가.
  • async def 안에 동기 I/O 가 없는가.

전체 체크리스트는 DEVELOPMENT §13 입니다.
