한 요청이 계층을 지나는 방식

flowchart LR Client --> Router Router --> Schema Router --> Dependency Dependency --> Service Service --> Repository Repository --> Session[AsyncSession] Session --> DB[(MySQL)] Service --> Policy[업무·소유권 정책] Router --> Response[Response DTO]

Router는 HTTP 계약과 commit 경계, Service는 유스케이스와 업무 분기, Repository는 SQL/ORM 데이터 접근을 담당합니다. 이 분리는 Repository Pattern, Service Layer, Dependency Injection, DTO, Composition Root를 작게 조합한 형태입니다.

새 기능 확장 순서

  1. 새 앱이 필요한지, 기존 기능의 endpoint 추가로 충분한지 먼저 결정합니다.
  2. 요청/응답 DTO, 권한, 데이터 소유권, read-only/writer 세션 의도를 정합니다.
  3. 기존 catalog(ORM) 또는 reports(Raw SQL)를 가장 가까운 예제로 복제하지 말고 구조만 따릅니다.
  4. 해당 저장소의 배선 방식에 맞춰 등록하고 migration·관리 화면·OpenAPI 태그를 연결합니다.
  5. 응답 DTO 검증 뒤 commit, 실패 시 rollback이라는 현재 트랜잭션 계약을 지킵니다.
  6. 기능 테스트, 라우트/권한 인벤토리, MySQL 통합 테스트와 문서를 갱신합니다.

상세 기능 개발 워크플로우와 개발 레퍼런스에서 파일별 절차를 확인하세요.

코드와 문서가 다르면 코드가 기준입니다. 변경 시 관련 소스·테스트·이 문서를 함께 갱신하세요.
