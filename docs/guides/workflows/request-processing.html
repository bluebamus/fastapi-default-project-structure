API 요청 처리 매뉴얼

클라이언트 요청이 미들웨어·DI·인증·Service·Repository·DB·응답을 지나는 전체 흐름입니다.

요청 처리의 전체 경계

요청은 ASGI 미들웨어를 통과한 뒤 FastAPI 라우팅·의존성 해석·Pydantic 검증을 거쳐 기능 Router로 전달됩니다. 조회는 read-only 의도를, 쓰기는 writer 세션을 주입받습니다. 인증과 인가는 endpoint 선언 및 Service의 소유권 정책으로 분리하고, 오류는 전역 handler가 일관된 ErrorResponse로 변환합니다.

sequenceDiagram participant C as Client participant M as CORS/UserInfo middleware participant F as FastAPI router + validation participant A as Auth/Access policy participant S as Feature service participant R as Repository participant D as AsyncSession/DB C->>M: HTTP request M->>F: request + client context F->>A: dependency graph A-->>F: Principal / deny 401·403 F->>S: validated DTO S->>R: use case query/command R->>D: ORM or named Raw SQL D-->>R: result R-->>S: domain data S-->>F: result F->>F: Response DTO validation F->>D: commit (write only) F-->>M: response M-->>C: status + JSON + access log

읽기와 쓰기의 차이

  • 읽기: read-only 세션을 선택하고 쓰기를 시도하면 거부합니다. 복제 구성이 켜지면 routing policy가 reader/writer를 결정합니다.
  • 쓰기: writer 세션을 사용합니다. Repository/Service가 임의로 commit하지 않고 HTTP handler가 성공 응답 직전 한 번 commit합니다.
  • 응답 DTO 검증을 commit보다 먼저 수행해, 직렬화/계약 실패가 데이터만 남기는 상황을 막습니다.
  • 세션은 요청 단위입니다. background task와 Celery는 별도 session context를 사용합니다.
