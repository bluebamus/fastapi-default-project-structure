2. 배선 — 라우터·모델·훅

2.1 라우터

자동 탐색도 중앙 목록도 없습니다. 세 단계를 명시적으로 거칩니다(AR-004).

# app/features/catalog/api/routers/router.py
catalog_router = APIRouter()
catalog_router.include_router(products_v1.router, prefix="/v1/catalog", tags=["Catalog"])

# app/features/catalog/__init__.py
from app.features.catalog.api.routers.router import catalog_router as router
from app.features.catalog.models import models as _models  # noqa: F401 (Base.metadata 등록)
__all__ = ["router"]

# main.py
from app.features import auth, blog, catalog, home, reply, reports, sns, user
app.include_router(catalog.router, prefix="/api")
  • 최종 URL 은 prefix 의 합입니다: v1/products.py 의 /products + /v1/catalog + /api = /api/v1/catalog/products. 디렉터리 이름이 URL 을 만들지 않습니다.
  • 기능명과 URL 세그먼트가 같아야 합니다 — tests/test_router_registration.py 가 /api/v1/<기능명>/ 으로 마운트 여부를 확인합니다.
  • 폴더가 있어도 main.py 에 없으면 라우트는 없습니다. 버전 세그먼트(/v1)는 설정이 아니라 각 router.py 가 직접 선언합니다(버전 설정 API_VERSION 은 읽는 코드가 없어 지웠습니다 — config-cleanup-2).
  • 기능 __init__.py 는 admin_views 를 재노출하지 않습니다(§12).

2.2 모델 메타데이터

라우터와 달리 모델은 디렉터리 구조가 진실의 원천입니다. models_registry.iter_model_modules() 가 app/features/*/models/models.py 를 찾아 정렬하고, import_all_models() 가 import 해 Base.metadata 를 채웁니다. auth 처럼 모델이 없는 기능은 건너뜁니다.

  • 소비처: app/core/resources.py(startup), migrations/env.py(Alembic), create_db_tables(import_models=True).
  • 그래서 main.py 에서 라우터를 빼도 폴더가 남아 있으면 모델은 여전히 테이블 생성·Alembic 대상입니다. 기능 제거는 라우터·테이블·데이터·migration 을 함께 판단합니다. 앱에서 빼도 DB 테이블은 지워지지 않습니다.
  • 모델 클래스가 import 되면 metadata 에 등록될 뿐, DB 에 테이블이 생기는 것은 개발용 create_all 또는 Alembic 입니다.

2.3 import 시점 훅

app/features/home/__init__.py 는 import 되는 순간 register_sink() 로 HomeAccessLogSink 를 미들웨어에 등록합니다(§10). 네트워크 연결이 아니라 프로세스 안의 참조 연결입니다.

3. 요청 처리 흐름

3.1 한 요청의 경로

요청 → UserInfoMiddleware → CORSMiddleware → 라우트
     → Depends: 세션 의존성(get_writer_db_session / get_read_only_db_session)
              → 기능 의존성 get_<name>_service[_readonly] → Service(db_session)
     → View 본문: Service 유스케이스 호출 → (쓰기면) await service.commit() → 응답 DTO
     → 응답 → UserInfoMiddleware 가 접속 로그 저장 태스크 제출 (§10)
     → 의존성 teardown: 세션 close (닫히면서 ROLLBACK 이 나간다)
계층 하는 일 하지 않는 일
View(api/routers/v1) 파라미터·본문 수신, Service 호출, 쓰기 커밋, 응답 DTO 변환, OpenAPI 메타데이터 SQL, AsyncSession 직접 주입, 복잡한 도메인 분기
Dependency 세션 선택 + Service(db_session) 조립 후 반환(yield 아님) 유스케이스 실행, 커밋
Service(BaseService) 유스케이스·비즈니스 규칙, 같은 세션으로 Repository 조립 HTTP 객체, SQL 문자열, 커밋 시점 결정
Repository ORM 쿼리 또는 Raw SQL, flush 까지 커밋, HTTP 응답, 비즈니스 규칙
Schema 입력 검증·응답 공개 필드·문서 DB 접근

미들웨어는 나중에 등록한 것이 바깥이라 UserInfoMiddleware 가 가장 바깥입니다. 같은 요청 안에서 같은 의존성 함수는 FastAPI 기본(use_cache=True)으로 한 번만 실행되지만, writer 와 read-only 는 다른 함수라 서로 다른 세션입니다.

3.2 트랜잭션 경계 — 쓰기 핸들러가 커밋한다

# dependencies — 조립만
async def get_catalog_service(
    db_session: AsyncSession = Depends(get_writer_db_session),
) -> CatalogService:
    return CatalogService(db_session)

# View — 응답 DTO 검증 → 커밋(한 번) → 반환
async def create_product(payload: ProductCreate, service: CatalogService = Depends(get_catalog_service)):
    product = await service.create_product(payload)
    response = ProductResponse.model_validate(product)
    await service.commit()
    return response
  • 성공: View 본문이 응답 DTO 를 검증한 뒤 응답을 반환하기 전에 await service.commit() (TX-004). 모든 쓰기 핸들러(catalog·blog·reply·sns·user·auth)가 이 순서이며, DTO 검증이 실패하면 커밋 0회로 500 이 됩니다(tests/test_write_dto_before_commit.py). reports 스냅샷 적재는 Service 가 커밋 전에 응답 DTO 를 만들어 돌려줍니다.
  • 예외: 커밋이 실행되지 않고 예외는 그대로 올라갑니다. 롤백은 async with 종료가 맡습니다 — AsyncSession.__aexit__ 이 shield 로 감싼 close() 를 실행하고 close() 가 ROLLBACK 을 보냅니다(ADR-031).
  • 조회: _readonly 의존성 → get_read_only_db_session, 커밋 0회(TX-002).
  • 요청 밖(background·Celery): async with background_db_session() as db_session: 에서 호출자가 직접 커밋합니다(별도 풀).

왜 의존성이 아니라 핸들러인가. 예전에는 의존성이 yield 뒤에서 커밋했습니다. FastAPI 0.141 로 올리자 기본 request scope 의 yield 의존성 종료 코드가 응답 전송 후 실행되어, 커밋이 실패해도 클라이언트가 201 을 받았습니다(scope="function" 은 종료 시점이 다릅니다 — 공식 설명). 커밋을 핸들러 본문으로 옮겨 실패가 응답 코드에 반영되게 했습니다. 구조 증거: tests/test_read_path_no_commit.py, app/features/blog/tests/test_transaction_boundary.py.

DB 커밋과 HTTP 전송은 하나의 원자적 작업이 아닙니다. 커밋 뒤 연결이 끊기거나 직렬화가 실패할 수 있으므로, 중복이 치명적인 생성 업무는 idempotency 정책을 따로 정합니다(DEVELOPMENT §4).

3.3 예외와 오류 응답

main.py 의 핸들러 4종(+ Redis 연결 오류 503)이 모든 오류를 ErrorResponse(error_code·message·detail)로 바꿉니다.

예외 응답
AppException 과 하위(NotFoundException·DuplicateException·DatabaseException…) 예외가 가진 상태 코드·error_code. 로그는 4xx 면 WARNING(detail 없음), 5xx 면 ERROR(detail 포함) — service-hardening ADR-008 ④
RequestValidationError 422, detail 에 field·message·type 목록. OpenAPI 의 422 도 이 ErrorResponse 로 광고한다 — FastAPI 기본 HTTPValidationError 는 앱 생성 시 후처리(main._openapi_with_actual_422)로 바꾼다(e2e-policy-2 결정 1, tests/test_openapi_contract.py)
Starlette HTTPException 해당 코드, error_code=HTTP_<코드>
redis ConnectionError·TimeoutError 503 SERVICE_UNAVAILABLE(fail-closed — 요청은 거부, 내부 정보 없음). 로그는 ERROR [RedisUnavailable] + traceback 한 번. 정상 응답으로 끝나 keep-alive 연결이 유지된다 — 아래 Exception 핸들러는 Starlette ServerErrorMiddleware 에 걸려 응답 뒤 예외를 다시 던지므로(uvicorn 이 traceback 을 한 번 더 남기고 연결을 닫는다) 그리로 보내지 않는다. 명령 오류(ResponseError 등)는 500 그대로 (integration-e2e ADR-009)
그 밖의 Exception 500 INTERNAL_SERVER_ERROR. DEBUG=true 면 detail 에 예외 문자열이 실린다 — 로그와 같은 redact() 로 비밀값을 가린 뒤(log-redaction ADR-001)

AppException·HTTPException 핸들러는 예외의 headers 를 응답에 그대로 싣습니다 — 405 Allow(라우팅이 채운다), 401 WWW-Authenticate: Bearer, 429 Retry-After(log-redaction ADR-002, tests/test_exception_headers.py). 401 은 예외가 헤더를 싣지 않았어도 두 핸들러가 WWW-Authenticate: Bearer 를 보탭니다(main._with_bearer_challenge) — 로그인 실패(InvalidCredentialsException)·refresh·logout·틀린 토큰(InvalidTokenException)까지 모든 401 이 같다(e2e-policy-2 결정 3). 405 의 Allow 는 Starlette 가 처음 걸린 라우트의 메서드로 채웁니다 — 같은 경로를 메서드별 함수로 나눈 곳 (GET·POST /api/v1/blog/posts)에서는 그 경로의 메서드 전부가 아니라 하나만 실립니다.

4.3 읽기/쓰기 라우팅

DB_ROUTER_ENABLED=true 면 create_routing_sessionmaker() 의 RoutingSession.get_bind() 가 구문마다 엔진을 고릅니다(app/core/db/router.py).

  1. ORM flush·Core DML·text() 의 쓰기 키워드(INSERT·UPDATE·DELETE·CREATE…), CTE 로 감싼 DML (WITH … UPDATE/DELETE), 잠금 읽기(FOR UPDATE·FOR SHARE·LOCK IN SHARE MODE, ORM select(...).with_for_update() 포함) → writer
  2. 그 밖의 SELECT → 세션당 하나의 replica(라운드로빈으로 고른 뒤 고정)
  3. 쓰기가 일어난 세션의 이후 SELECT → writer (DB_READ_STICKY_AFTER_WRITE=true, 기본)
routing_mode 조건 결과
single DB_ROUTER_ENABLED=false(기본) 단일 엔진 세션. 라우팅만 없고 읽기 세션의 쓰기 차단은 동작한다
router-single 라우터만 켬 전부 primary
router-replicated 라우터 + 복제 + MYSQL_REPLICA_HOSTS SELECT → replica, 쓰기 → primary

읽기 세션의 쓰기 차단은 위 모드와 무관합니다. app/core/db/router.py 가 Session 기반 클래스에 before_flush·do_orm_execute 리스너를 전역 등록하므로, 어떤 sessionmaker 로 만든 세션이든 mark_read_only() 가 걸린 세션에서는 ORM flush·Core DML·Raw text() DML 이 ReadOnlyRoutingError 로 거부됩니다. 판정은 default-deny 이고 절차는 DEVELOPMENT §7.2 에 있습니다.

  • replica 장애: 읽기 전용 세션(get_read_only_db_session)의 읽기가 replica 연결 오류(MySQL 2002·2003·2006·2013 또는 SQLAlchemy 가 연결을 무효화한 오류 — 접속 불가·연결 끊김·타임아웃)로 실패하면 RoutingSession 의 do_orm_execute 리스너가 같은 구문을 primary 로 한 번 다시 실행하고 WARNING [database] replica 연결 실패(<타입>(code=…)) 를 남깁니다(호스트·DSN 없음). 그 세션은 이후 primary 에 고정됩니다. 쿼리 문법·제약 오류는 재시도하지 않고, 읽기 전용이 아닌 세션(writer·투명 라우팅)도 재시도하지 않습니다 — 쓰기와 한 트랜잭션에 섞일 수 있어서입니다. replica 가 없으면(단일 DB) 동작 변화가 없습니다. /ready 는 그대로 writer·Redis 만 봅니다(integration-e2e ADR-010).
  • 인증 사용자 조회는 primary: get_current_user(/me)는 읽기 전용 세션에 using_writer() 를 더해 primary 에서 읽습니다 — 복제 지연 동안 막 가입한 사용자의 유효한 토큰이 401 이 되지 않고, 비활성화·삭제가 즉시 반영됩니다. 쓰기 차단은 그대로이고 나머지 읽기 라우팅은 바뀌지 않습니다(e2e-policy-2 결정 5).
  • 복제만 켜고 라우터를 끄거나 replica 목록이 비면 DatabaseSettings 가 기동 시 거부합니다. replica 주소는 host·host:port·[IPv6]:port 만 허용합니다.
  • 기동 로그 [database] 라우팅 구성: {...} 에 모드와 비밀번호를 가린 DSN 이 남습니다(URL.render_as_string(hide_password=True)).
  • DSN 은 문자열로 조립하지 않고 config.mysql_url() → sqlalchemy.engine.URL.create() 로 만듭니다. MYSQL_URL·MYSQL_WRITER_URL·MYSQL_REPLICA_URLS·ALEMBIC_URL 은 URL 객체이고, 비밀번호의 @ : / # % ? 와 IPv6 호스트가 그대로 왕복합니다(tests/core/test_dsn.py, service-hardening ADR-004).
  • 라우팅 판별(_text_is_write)과 읽기 세션의 차단 판별(_text_is_readable)은 방향이 반대인 별개지만 같은 괄호 깊이 0 스캐너(_depth0_words)를 씁니다. 둘 다 WITH … UPDATE/DELETE 를 잡습니다(ADR-036). 잠금 읽기도 같은 _LOCKING_READ 정규식 하나로 판정합니다 — FOR UPDATE·FOR SHARE· LOCK IN SHARE MODE 전부입니다. 다만 적용 대상은 다릅니다: 라우팅(_text_is_write)은 깊이 0 단어 목록에 적용해 WHERE note = 'for share' 같은 리터럴에 걸리지 않지만(ADR-038), 차단(_text_is_readable)은 주석만 걷어낸 원본 문자열에 적용하므로 그런 리터럴도 거부합니다(fail-closed). 스캔이 무너지면 라우팅은 writer 로(fail-safe), 차단은 거부로(fail-closed) 기웁니다.
  • ORM 잠금 읽기(with_for_update(), read=True 포함)는 문자열이 아니라 Select._for_update_arg 로 판정합니다(_is_locking_select). 라우팅은 writer, 읽기 세션은 거부 — text 의 FOR UPDATE 와 같습니다 (service-hardening ADR-005). sticky 는 세션 안의 정책이라 다음 요청의 복제 지연까지 없애지 않습니다. 읽기 전용 표시는 DB 권한을 대신하지 않으므로 운영에서는 replica 전용 읽기 계정 (MYSQL_REPLICA_USER)을 함께 씁니다.

6. 설정

6.1 로딩 규칙

  • config.py 의 10개 BaseSettings 는 각각 env_file=".env", extra="ignore" 로 자기 필드를 읽습니다. 우선순위는 프로세스 환경 변수 → 작업 디렉터리의 .env → 코드 기본값입니다.
  • get_*_settings() 는 @lru_cache 이고, 파일 끝의 app_settings = get_app_settings() 등이 import 시점에 전역 객체를 만듭니다. 실행 중 .env 를 바꿔도 반영되지 않습니다. 테스트에서 캐시만 비워도 이미 가져간 전역 참조는 그대로이므로 새 프로세스나 monkeypatch 로 확인합니다.
  • 타입 오류·validator 위반은 config import 자체를 실패시켜 lifespan 전에 기동을 막습니다. validator: 복제 설정 모순·replica 주소 형식(DatabaseSettings), CORS_ALLOW_ORIGINS=["*"] + CORS_ALLOW_CREDENTIALS=true(CORSSettings), 관리 세션 미사용 만료 > 절대 만료(SessionSettings).
  • 전역 객체를 만든 뒤 파일 끝에서 설정 검사 세 개가 차례로 돕니다. 모두 RuntimeError 로 config import 를 실패시키고, 메시지에는 설정 이름만 나옵니다. ENV=test 는 모두 건너뜁니다(pytest 가 지정). 1. validate_env_source() — 출처(ADR-045 ①). .env 가 없으면 ENV·비밀 키 3종·MYSQL_HOST/USER/PASSWORD/DATABASE (REQUIRED_WITHOUT_ENV_FILE)가 환경 변수로 모두 있어야 합니다. 컨테이너 주입은 통과하고, 아무것도 없으면 멈춥니다. 2. validate_no_legacy_admin() — 예전 이름(admin-login ADR-005).     • test 외 모든 ENV(ADR-027·030·045 ②): ACCESS_TOKEN_SECRET_KEY·REFRESH_TOKEN_SECRET_KEY·SESSION_SECRET_KEY·MYSQL_PASSWORD 가 예시 값(change-this 포함·your- 시작·빈 값), 비밀 키 3종이 32자 미만, access 와 refresh 가 같음. REDIS_PASSWORD 는 값이 있을 때만 예시 값인지 봅니다 — 비밀번호 없는 사설망 Redis 가 정당한 구성이라 빈 값은 통과합니다.

  • 환경 변수를 직접 읽는 곳은 config.py 뿐입니다(tests/core/test_settings_contract.py).

7. 기동

7.1 import 시점

uv run python main.py 는 main 을 import 해 조립한 뒤 run_server() 가 uvicorn.run("main:app", …) 을 부르고, uvicorn main:app 은 uvicorn 이 main 을 import 합니다. 어느 쪽이든 순서는 같습니다.

  1. config — 설정 생성·검증, 배포 안전 검사(validate_deployment_safety(), §6.1)
  2. get_logger() 첫 호출 → configure_logging() — dictConfig 적용, listener 시작, atexit·신호 훅 등록(§9.5)
  3. app/core/db/session.py — 엔진·세션 팩토리 생성, 라우팅 구성 로그
  4. app.features 각 패키지 — 라우터·모델 import, home 의 sink 등록
  5. FastAPI(...) → 미들웨어 → 예외 핸들러 → include_router × 8 → health/ready//docs → ADMIN_DISABLED 가 아니면 SQLAdmin 마운트(인증 백엔드·세션 미들웨어 포함) → AccessPolicyGuard().verify(app)(접근 수준 검사 — 위반이면 import 실패, §11.2)

reload·다중 worker 는 새 프로세스마다 이 과정을 반복하므로 Redis client·DB 풀·listener 는 프로세스마다 따로 있습니다.

8. 종료

8.1 순서와 강제 방식

순서를 강제하는 코드는 없습니다. 중첩 컨텍스트가 곧 순서이고, 파이썬이 역순으로 풉니다(ADR-017).

uvicorn: 신규 요청 수신 중단 → 진행 중 요청 처리 → lifespan shutdown
① _background_tasks  "[shutdown] 애플리케이션 요청 처리 자원 해제 시작" → 접속 로그 태스크 drain
② _redis             app.state.redis = None → client.aclose()
③ _database          dispose_engine() — writer·replica·background 를 gather 로 동시에
                     → app.state.resources = None → "[shutdown] 애플리케이션 요청 처리 자원 해제 완료"
④ _log_queue         flush_log_queue() — 쌓인 로그가 다 쓰일 때까지 **기다린다**(멈추지 않는다)
uvicorn: "Application shutdown complete" · "Finished server process"
프로세스 종료: atexit / 신호 핸들러 → stop_log_listener()  ("[log-lifecycle] stop 완료", stderr 직접)
  • ①이 ②③보다 먼저인 이유: 외부 자원을 쓰는 주체(background task)가 살아 있는데 client·풀을 닫으면 연결이 강제로 끊깁니다.
  • ④가 마지막인 이유: 앞 단계가 남긴 로그까지 내보내야 합니다.
  • 이 중첩을 평평한 finally 안의 연속 await 로 되돌리지 마세요. asyncio.CancelledError 는 BaseException 이라 _run_cleanup() 의 except Exception 을 통과하고, 연속 await 였을 때는 첫 단계에서 취소를 맞으면 뒤 단계가 통째로 건너뛰어졌습니다(DB 풀이 닫히지 않았다). 중첩 컨텍스트는 취소가 전파되어도 바깥 __aexit__ 를 시도합니다. 회귀 테스트: tests/core/test_resources.py::test_manager_cancellation_still_runs_remaining_cleanup.
  • 요청별 AsyncSession 은 이 사슬 밖에서 세션 의존성이 닫습니다. Celery worker 의 연결은 worker 가 닫습니다(AR-006, §13). 종료에서 테이블을 drop 하지 않습니다.

8.4 보장하지 않는 것

  • SIGKILL(kill -9, 유예 초과) — 어떤 정리도 실행되지 않습니다. DB 연결은 서버 측 timeout 이 정리하고, 큐에 남은 로그는 사라집니다.

  • 반복 취소·무응답 I/O 에서 모든 정리의 성공, 다중 worker(gunicorn 등)·POSIX 실경로의 신호 처리는 실행 검증하지 않았습니다(CRP residual-risk 참고).

9.1 큐를 거치는 이유와 포화 정책

stdout·stderr 쓰기는 느린 동기 I/O 라 요청 스레드에서 하면 event loop 전체가 멈춥니다. 그래서:

요청 코드 ─ put_nowait ─▶ [bounded queue 10,000] ─▶ QueueListener 스레드 ─▶ stdout / stderr / 파일(LOG_FILE_ENABLED)

root 로거에는 BoundedQueueHandler 하나만 붙고, 필터(SqlNoiseFilter, RedactingFilter, ContextFilter, AppLevelFilter)는 적재 전에 요청 스레드에서 돕니다(ContextFilter 는 호출 스택에서 클래스명을 뽑으므로 listener 스레드에서는 늦습니다). 파일 쓰기·회전도 listener 스레드가 하므로 요청 event loop 를 막지 않습니다.

logger.info() 가 반환됐다고 출력된 것은 아닙니다. 임계값·필터에서 걸러질 수 있고, 큐가 차면 버려질 수 있으며, 큐에 들어갔더라도 listener 가 쓰기 전에 프로세스가 죽으면 사라집니다(listener 는 daemon 스레드입니다). 아래 설계는 전부 이 성질에서 나옵니다.

큐가 가득 찼을 때 처리
DEBUG·INFO·WARNING 버리고 dropped 증가, 5초에 한 번 [log-fallback] log queue full — dropped N record(s)
ERROR·CRITICAL logging API 를 다시 타지 않고 sys.stderr 에 최소 포맷으로 직접 기록, fallbacks 증가

producer 를 막는 선택지는 쓰지 않습니다 — 로그 때문에 API 가 느려지는 것이 로그 몇 줄을 잃는 것보다 나쁩니다. 관측 지표: BoundedQueueHandler.dropped/fallbacks, access_log_tasks.dropped/cancelled.

build_dictconfig()(app/utils/logs/config.py)가 유일한 설정 지점이며 ENV 로 갈립니다.

ENV 출력 시각

test stdout 설정 타임존

기본은 파일이 없고 저장·검색·rotation 은 Docker·Kubernetes·수집 agent 가 맡습니다. LOG_FILE_ENABLED=true 면 설정 로드 직후(configure_logging(), 첫 get_logger()) 실행 프로그램 sys.argv[0] 으로 프로세스 종류를 정해 setup.attach_log_files() 로 listener 에 파일 핸들러를 더합니다(setup.entry_process()) — python main.py·uvicorn (-m uvicorn 포함)은 app.log·error.log, celery(-m celery, worker·beat)는 celery.log·celery-error.log. 그래서 import 중에 찍히는 줄([database] 라우팅 구성 등)도 파일에 남습니다. 그 밖의 프로그램(pytest·alembic·스크립트)은 파일을 열지 않고, 진입점의 호출(main.py import, Celery after_setup_logger 수신자)이 그 판정을 못 하는 실행을 덮습니다 — 여러 번 불러도 한 번만 붙습니다(integration-e2e ADR-011 이 logging-overhaul ADR-002 의 "진입점이 정한다"를 대체). 에러 파일도 프로세스별로 나눈 이유는 웹과 worker 가 한 파일을 회전시키지 않게 하려는 것입니다 (logging-overhaul ADR-002). 핸들러는 DailySizeRotatingFileHandler(app/utils/logs/handlers.py) 하나입니다 — 매일 자정(포매터와 같은 시간대)에 app.log.YYYY-MM-DD, 하루 안에서 LOG_MAX_SIZE_MB 초과면 .1·.2…, 교체 때 LOG_RETENTION_DAYS 보다 오래된 날짜 파일(분할 포함)을 지웁니다. 이미 있는 이름은 덮지 않고 다음 번호를 씁니다. uvicorn --workers 2 이상·Celery prefork 처럼 여러 프로세스가 같은 파일을 쓰면 회전이 엇갈리므로 파일을 끄고 콘솔 + 수집기를 씁니다(README "여러 워커 주의").

포맷은 LOG_CONSOLE_FORMAT·LOG_FILE_FORMAT(style="{"), 시각은 LOG_DATE_FORMAT(strftime)이 정하고 console_formatter_kwargs()·file_formatter_kwargs() 가 TzFormatter 에 넘깁니다. 기본값(= LOG_FORMAT)은 다음과 같습니다:

[{asctime} {tzname}] {levelname:5} [app={appname}] [{module}:{classname}:{funcName}:{lineno}] {message}
[2026-09-17 16:29:05.704 KST] INFO  [app=core] [session:-:<module>:166] [database] 라우팅 구성: {...}
  • 필드는 LogRecord 속성과 TzFormatter 가 채우는 {tzname}·{appname}·{classname}. 설정 로드 때 샘플 레코드를 한 번 포맷해 보고, 모르는 필드·괄호 불일치·잘못된 서식 지정자·빈 날짜 형식이면 기동을 멈춥니다. 필수 필드(config.LOG_REQUIRED_FIELDS — {asctime}·{levelname}·{appname}·{module}·{classname}· {funcName}·{message})가 하나라도 빠져도 빠진 목록과 함께 기동을 멈춥니다.
  • 시각: development 는 날짜 형식 뒤에 밀리초(.704)가 붙고, staging·production 은 UTC 로 렌더합니다.
  • 비밀값 마스킹(§9.4.1)은 queue 적재 전 필터라 포맷과 무관합니다.
  • LOG_CONSOLE_ENABLED=false 면 콘솔(stdout/stderr) 핸들러를 하나도 만들지 않습니다. 판단은 console_enabled() 한 곳이고, 앱 dictConfig 가 그것을 보며 uvicorn CLI·Celery 의 콘솔 핸들러는 공유 queue 로 바뀌어 같은 결정을 따릅니다. 파일 출력(LOG_FILE_ENABLED·Celery --logfile)은 남습니다. 파일도 꺼져 있으면 앱 로그는 버려지고, 기동 때 stderr 에 [logging] 경고: LOG_CONSOLE_ENABLED=false … 한 줄이 나옵니다.

  • 모든 실행 경로가 같은 형식입니다(logging-overhaul L1). uvicorn main:app(·fastapi dev) CLI 와 Celery worker 는 자기 콘솔 핸들러를 다는데, setup.adopt_foreign_handlers() 가 그것을 떼고 공유 queue 핸들러를 답니다 — CLI 는 configure_logging() 이 uvicorn 로거 3종에, Celery 는 after_setup_logger·after_setup_task_logger 수신자가. 핸들러가 없던 로거(--no-access-log)는 그대로 두고, Celery --logfile 파일 핸들러는 남긴 채 LOG_FILE_FORMAT 과 같은 필터만 입힙니다. uvicorn 접속 줄은 요청 줄(client - "GET /p HTTP/1.1" 200)을 {message} 로 담습니다 — uvicorn AccessFormatter 가 만드는 상태 문구(OK)는 빠집니다.

  • app= 은 판별 함수 하나(filters._app_from_path(pathname, logger_name))가 정합니다. 우리 코드는 소스 경로로: 기능명(app/features/<name>/), core·celery·utils·migrations, 그 밖의 저장소 코드는 app. 저장소 밖 코드는 로거 이름으로: celery.*·kombu.* → celery, uvicorn.* → uvicorn, sqlalchemy.* → sqlalchemy, alembic.* → alembic, 그 밖은 ext. ContextFilter 를 거치지 않은 줄도 TzFormatter 가 같은 함수로 헤더를 채웁니다.

  • classname 은 LoggerMixin(self.log)이면 주입값, 아니면 호출 프레임의 self/cls, 없으면 -.
  • 앱별 로거를 dictConfig 에 등록하지 않습니다(charter §2-4, 가드 test_dictconfig_has_no_per_app_loggers). 새 기능이 로깅 설정을 건드릴 일이 없습니다. 헤더별 레벨은 로거 대신 필터(AppLevelFilter, §9.3)로 줍니다.

9.3 레벨이 정해지는 방식

root 와 console 핸들러의 임계값이 각각 정해지고, 둘 다 통과해야 출력됩니다.

  • root = LOG_LEVEL 이 있으면 그 값, 없으면 DEBUG=true → DEBUG, false → INFO
  • console = LOG_CONSOLE_LEVEL 이 있으면 그 값, 없으면 같은 규칙
DEBUG LOG_LEVEL / LOG_CONSOLE_LEVEL 보이는 것
false 미설정 / 미설정 INFO 이상
true 미설정 / 미설정 DEBUG 이상
false DEBUG / DEBUG DEBUG 이상 (앱은 여전히 DEBUG=false 모드)
true WARNING / WARNING WARNING 이상 — startup INFO 도 안 보인다
무관 INFO / DEBUG INFO 이상 (root 가 DEBUG 를 먼저 막는다)
무관 DEBUG / INFO INFO 이상

[startup] 애플리케이션 자원 초기화 시작 (DEBUG=%s) 의 DEBUG 는 표시값일 뿐 출력 조건이 아닙니다. uvicorn 로거 레벨은 python main.py 경로에서 root 와 같은 규칙(LOG_LEVEL/DEBUG)을 따릅니다.

헤더별 레벨 LOG_APP_LEVELS("blog=DEBUG,celery=INFO,sqlalchemy=WARNING")는 Django LOGGING["loggers"][name]["level"] 자리입니다. root·queue·uvicorn 로거 레벨은 LOG_LEVEL 과 이 값들 중 최솟값(config.lowest_level())으로 내려 레코드가 필터까지 오게 하고, queue 의 ContextFilter 바로 뒤 AppLevelFilter 가 헤더별 최소 레벨(지정 없으면 LOG_LEVEL)보다 낮은 레코드를 버립니다. 잘못된 형식·레벨은 기동 오류, 모르는 헤더는 WARNING 한 줄입니다. 파일은 LOG_FILE_LEVEL(없으면 같은 규칙), 에러 파일은 ERROR 고정. Celery worker 의 root 레벨은 celery -l 이 정합니다.

9.4 SQL 로그 차단

DEBUG=true 면 유효 레벨이 DEBUG 라 SQLAlchemy·드라이버가 실행 SQL 과 바인딩 값(비밀번호 해시·토큰· 검색어)을 찍습니다. SqlNoiseFilter 가 sqlalchemy.engine·sqlalchemy.pool·aiosqlite·aiomysql· asyncmy·pymysql 로거의 WARNING 미만을 막습니다(장애는 계속 보입니다). SQL 을 봐야 할 때만 LOG_SQL_ECHO_ENABLED=true 로 엽니다(NFR-001, tests/core/test_sql_logging_leak.py).

9.4.1 비밀값 마스킹 — traceback 포함

RedactingFilter(app/utils/logs/filters.py)가 메시지·traceback·stack_info 의 비밀값을 *** 로 가립니다. 규칙의 정본은 같은 파일의 redact() 하나이고 DEBUG 500 응답의 detail 도 이것을 씁니다(log-redaction ADR-001).

가리는 형태 예
DSN 계정(사용자명·비밀번호) mysql+asyncmy://***:***@h/db · redis://:***@cache:6379/0
설정 비밀값 원문(config.LOG_SECRET_SETTINGS — DB 계정·비밀번호, Redis 비밀번호, JWT·세션 키) 어디에 나오든 ***. 4글자 미만 값은 user=·username= 형태에서만
Authorization 값·Bearer 토큰 Authorization: Bearer ***
이름에 password·passwd·pwd·secret·token·api_key 가 든 키의 값 password=*** · "refresh_token": "***"

traceback 은 보통 포매터가 나중에 exc_info 에서 만들어 필터가 볼 수 없습니다. 그래서 필터가 exc_info 를 미리 exc_text 로 포맷해 가려 둡니다(포매터는 exc_text 가 있으면 다시 만들지 않는다). exc_info 는 남겨 예외 타입·체인·파일·줄은 그대로 보입니다. 메시지는 가릴 것이 있을 때만 바꿉니다. 비밀값이 인자 하나 안에만 있으면 그 인자만 가리고 args 모양을 지킵니다 — args 를 직접 푸는 uvicorn access 포매터가 깨져 접속 줄이 사라지지 않게 (config-cleanup F-008). 틀과 인자에 걸치면("password=%s") 합친 문자열로 바꿉니다.

출력 경로 붙는 곳
앱·SQLAlchemy·python main.py 의 uvicorn 로거 root 의 queue 핸들러 필터 redact — stdout·stderr·큐 포화 fallback 모두
uvicorn main:app CLI 의 uvicorn·uvicorn.error·uvicorn.access 콘솔 핸들러가 공유 queue 로 바뀌어 queue 필터를 탄다. configure_logging() 이 그 로거에도 붙여 둔다. 접속 줄의 ?token=… 도 가려지고 요청 줄은 남는다
Celery worker 콘솔은 공유 queue, --logfile 파일 핸들러에는 after_setup_logger·after_setup_task_logger 수신자가 같은 필터를 붙인다(app/celery/lifecycle.py)
파일(LOG_FILE_ENABLED) listener 의 출력처라 queue 필터를 이미 거친 레코드만 쓴다

형태로 찾는 규칙이라 모든 비밀을 잡지는 못합니다 — 비밀값을 로그·예외 메시지에 넣지 않는 것이 먼저입니다 (tests/utils/test_log_redaction.py).

9.5 listener 수명 — 프로세스가 소유한다

listener 는 FastAPI lifespan 보다 오래 살아야 합니다. lifespan 에서 멈추면 그 뒤에 uvicorn 이 남기는 최종 로그와 startup 실패 traceback 이 소비자 없는 큐에 갇힙니다 — 실제 증상은 "DB 가 꺼진 채 서버를 띄우면 오류 원인이 한 글자도 안 나온다"(14줄 출력, traceback 0건)였습니다(ADR-018).

장치 위치 하는 일
시작 configure_logging() dictConfig 가 만든 handler.listener(TimeoutSentinelListener)를 시작 — Celery·Alembic·테스트처럼 lifespan 이 없는 프로세스에서도 로그가 나간다
atexit 훅 같은 곳, 프로세스당 1회 정상 종료·sys.exit·Ctrl+C(SIGINT → KeyboardInterrupt)에서 stop_log_listener()
SIGTERM·SIGBREAK 핸들러 같은 곳, main thread 에서만 이 신호들은 기본 동작이 즉시 종료라 atexit 이 돌지 않는다(docker stop·Kubernetes·Windows Ctrl+Break). 로그를 비우고 → SIG_DFL 로 되돌려 → 같은 신호를 다시 올린다. 신호를 삼키지 않는다(삼키면 컨테이너가 안 죽어 SIGKILL 까지 간다). 이미 다른 핸들러가 있으면 건드리지 않는다(gunicorn·Celery)
SIGINT — 일부러 건드리지 않는다 — KeyboardInterrupt 를 기대하는 pytest·REPL·디버거가 달라진다
lifespan 끝의 flush _log_queue() → flush_log_queue() 멈추지 않고 unfinished_tasks == 0 을 2초까지 기다린다(ADR-023). Queue.join() 과 같은 조건이지만 timeout 이 있어야 listener 가 죽었을 때 매달리지 않는다
포화 시 정지 TimeoutSentinelListener enqueue_sentinel() 오버라이드로 sentinel 적재에 2초 예산(stdlib 가 지정한 확장 지점, ADR-021), stop() join 에 5초 예산
fork 후 재시작 restart_log_listener() Celery prefork 자식에서 스레드를 다시 세운다(§13)

⚠️ app/core/resources.py 에 listener 정지 코드를 넣지 마세요. 기다리기(flush)는 되지만 멈추기(stop)는 프로세스의 몫입니다. stop_log_listener_async() 는 공개돼 있지만 lifespan 은 호출하지 않습니다.

  • user_access_logs 테이블의 country·country_code·city 컬럼은 채우는 코드가 없습니다. 인덱스: created_at·ip_address·os_name·browser_name·device_type·country·session_id·user_id.
  • session_id 쿠키 값·referer·forwarded_for(X-Forwarded-For)·real_ip 는 원문 그대로 저장합니다 — 사용자 결정으로 유지합니다(log-redaction ADR-004). 조회 API 는 슈퍼유저 전용입니다.
  • 보존(security-ops-hardening ADR-002·ADR-003) — Celery beat 가 매일 03:30(TIME_ZONE 기준) home.purge_expired_access_logs 를 실행해 created_at < 지금(UTC) − ACCESS_LOG_RETENTION_DAYS 일 인 행을 지웁니다(정확히 N일 전 행은 남는다). 정책은 AccessLogRetentionService(보존 일수·시계 주입), 쿼리는 UserAccessLogRepository.delete_created_before — created_at 인덱스로 id 를 최대 5,000개 고른 뒤 DELETE ... WHERE id IN (...) 하고 배치마다 커밋합니다(긴 잠금·거대 트랜잭션 방지, MySQL·SQLite 공통 쿼리). 0 이면 쿼리 없이 끝납니다. beat 를 띄우지 않으면 아무것도 지워지지 않습니다(§13).
  • X-Forwarded-For 는 클라이언트가 위조할 수 있으므로 신뢰 프록시 홉 수(TRUSTED_PROXY_HOPS) 밖의 값은 믿지 않습니다. 이전에는 맨 왼쪽 값을 무조건 믿었습니다 — 기본값 0 은 이 동작을 바꾼 것이니 프록시 뒤 배포는 홉 수를 설정해야 실제 클라이언트 IP 가 기록됩니다.
  • BackgroundTaskRunner 는 동시 256개가 상한이고 넘치면 버리고 dropped 를 올립니다. 비핵심 로그용이라 결제·발송 같은 업무 저장을 이 러너에 넣지 않습니다. 종료 시 drain 합니다(§8).
  • 저장 실패는 요청에 영향을 주지 않고 ERROR 로그만 남깁니다. 제출 시점은 call_next 가 응답 객체를 돌려준 뒤이며, 클라이언트가 본문을 다 받았다는 보장은 아닙니다. call_next 가 예외로 끝난 요청은 status 500 으로 기록한 뒤 예외를 그대로 다시 던집니다(바깥 500 처리는 그대로 — service-hardening ADR-007).
  • 조회 API 는 /api/v1/home/access-logs 계열 5개(전부 읽기 세션)이고, 예시 Celery 태스크 home.aggregate_access_stats 가 통계를 집계합니다.

비밀번호 — PasswordHasher (app/core/security/password_hasher.py — auth 의 가입·로그인과 user 의 관리자 생성이 함께 쓴다, ADR-026) - 새 해시는 Argon2id(pwdlib). 이전 버전의 bcrypt 해시($2 접두사)는 그때 규칙(UTF-8 72바이트 절단)으로 검증하고, 맞으면 Argon2 로 다시 해시해 로그인 핸들러가 커밋합니다(점진 이전 — 그 밖의 로그인은 커밋하지 않습니다). - 상수 시간 인증: 사용자가 없거나 비밀번호가 없어도 더미 Argon2 해시로 같은 비용을 치릅니다. 논블로킹 해싱: 해시·검증은 asyncio.to_thread 에서 돕니다.

토큰 — TokenService (app/core/security/tokens.py) - claims sub, type, iat, nbf, exp, jti(uuid4 hex), iss, aud + access 는 username·su(슈퍼유저 여부), refresh 는 fam(회전 family). access 의 username·su 는 필수입니다 — su 가 없는 토큰(인가 도입 전 발급분)은 401 이고 다시 로그인하면 됩니다. - 검증: 알고리즘은 설정 하나(algorithms=[JWT_ALGORITHM]), iss·aud 일치, 위 claim 전부 필수, leeway, type 일치. access·refresh 는 서명 키도 다릅니다. 실패는 사유와 관계없이 InvalidTokenException(401, AUTH_INVALID_TOKEN).

회전·폐기 — RefreshTokenStore (app/core/security/refresh_store.py, Redis)

  • logout: family 폐기, 204. 이미 폐기됐어도 204(멱등). access 토큰은 폐기하지 않습니다 — 만료(기본 15분)까지 유효합니다.

11.1 인가 — Principal · 슈퍼유저 · 소유권

인가는 슈퍼유저/일반 2단계입니다(service-hardening ADR-017·018). RBAC 세분화는 비목표입니다.

  • Principal(id, username, is_superuser) (app/core/security/authorization.py, frozen dataclass) — access 토큰의 sub·username·su 로만 만듭니다. 요청마다 DB·Redis 왕복이 없고, 기능은 사용자 모델 대신 이 값 하나에 기댑니다. get_current_principal 이 만들고 request.state.user_id 를 채웁니다 — 접속 로그 미들웨어가 응답 뒤에 읽어 user_access_logs.user_id 에 남깁니다(§10).
  • 별칭 — 인자용 CurrentPrincipal(로그인)·SuperuserPrincipal(슈퍼유저), 데코레이터용 접근 수준 LoginRequired·SuperuserRequired·Public·PublicWrite(§11.2 — 뷰마다 하나 선언, 없으면 기동 거부). 토큰 문제는 401(WWW-Authenticate: Bearer), 권한 부족은 403 FORBIDDEN.
  • OwnershipPolicy.ensure_can_modify(owner_id, principal) — 소유자 본인 또는 슈퍼유저만 통과. owner_id 가 None (인가 도입 전 행)이면 슈퍼유저만. blog·sns·reply·user 서비스가 생성자로 받고 수정·삭제(user 는 단건 조회 포함) 메서드가 principal 을 받아 부릅니다. 존재 확인(404)이 먼저이고 user 만 반대로 권한이 먼저입니다(남의 ID 로 계정 존재를 캐지 못하게).
  • 스키마 — users.is_superuser(기본 false), blog·sns·reply 의 author_id(String(36), NULL, 인덱스, FK 없음 — 기능 모델끼리 참조하지 않는다). 리비전 c9e1a3b5d7f0. 작성자(author·author_id)는 생성 시 서버가 주체로 채우고 수정 스키마에 없습니다.

11.2 접근 수준 선언과 기본 거부

모든 API 뷰는 접근 수준을 하나 선언합니다(access-policy ADR-001~003). 경로 데코레이터의 dependencies=[...] 에 넣는 Depends 객체 넷이 app/core/security/access.py 에 있습니다.

수준 정체 쓰는 곳 실패
Public 아무것도 하지 않는 async 표식 함수 인증 없는 조회 — GET·HEAD·OPTIONS 만 —
PublicWrite 또 다른 표식 함수 인증 없는 쓰기를 의도적으로 연다 — 가입·로그인·refresh·logout —
LoginRequired Depends(get_current_principal) 로그인 401

  • 태스크 본문의 서비스 조립은 그 기능의 provider 함수(세션을 인자로 받는 일반 함수, 예: build_user_access_log_service(session))를 재사용합니다 — HTTP provider 도 같은 함수를 부릅니다.

  • 태스크 함수는 동기이고 내부 코루틴은 run_async()(app/celery/task.py)로 실행합니다. 프로세스당 영속 event loop 를 재사용합니다 — aiomysql 연결은 만든 루프에 묶이는데, 매번 asyncio.run() 으로 루프를 닫으면 두 번째 태스크가 Event loop is closed 로 실패했습니다. 태스크 안 DB 는 background_db_session().
  • 수명(app/celery/lifecycle.py, AR-010): worker_process_init → restart_log_listener()(fork 로 사라진 listener 스레드 복구). worker_process_shutdown → 루프가 살아 있는 동안 dispose_engine()(10초) → shutdown_asyncgens() → loop.close() → 루프 참조 제거. FastAPI lifespan 과 소유권이 섞이지 않습니다.
  • 요청의 세션·Service·Request 객체를 태스크 인자로 넘기지 않습니다 — JSON 직렬화 가능한 id·값만 넘기고 태스크가 자기 세션을 엽니다. 재시도·중복 처리는 태스크마다 정합니다.

15. 설계 결정 요약

결정 이유
라우터는 main.py 명시 include_router (FastAPI Bigger Applications 패턴) 로딩 순서와 공개 API 구성을 코드에서 바로 추적할 수 있다. 앱 레지스트리·자동 탐색·INSTALLED_APPS 식 목록은 한 번씩 도입했다가 제거했다(§16)
모델은 디렉터리 스캔 모델 import 목록이 세 곳에 복제돼 한쪽만 고치는 누락이 있었다
UnitOfWork 없음 — 쓰기 핸들러가 커밋 FastAPI 0.141 의 yield 의존성 종료 시점 변화에서 커밋 실패가 2xx 로 둔갑했다(§3.2)
BaseRepository 를 최소 CRUD 8개로 사용처 0건인 고급 메서드 20종을 제거했다. 공통성은 두 기능 이상에서 확인될 때만 올린다(ADR-007)
ORM·Raw Base 독립 Raw 결과에 ORM 의미가 새지 않게(AR-003)
로그는 큐 + stdout/stderr, 파일 없음, 앱별 로거 없음 event loop 비차단(NFR-009), 수집은 런타임 책임, 새 기능이 로깅 설정을 건드리지 않게
표준 라이브러리 우선 · 자원은 소유자가 닫는다 · 실패와 취소를 구분한다 · 테스트 없는 보장은 문서에 쓰지 않는다 종료 신뢰성 작업(REQ-010)의 원칙
Redis(서버 6.2 이상 — GETDEL)는 필수 startup 조건이자 /ready 판정 대상 Celery broker 와 같은 서버가 준비됐는지 기동 시점에 드러낸다(REQ-011). 기동 후 Redis 가 끊기면 /ready 가 503 으로 트래픽을 뺀다(service-hardening ADR-011). 그동안 Redis 를 쓰는 API 는 503 SERVICE_UNAVAILABLE(§3.3, integration-e2e ADR-009)
관리 화면은 기본 켜짐 + 활성 슈퍼유저 로그인, ADMIN_DISABLED=true 로 흔적 없이 끈다 개발 우선 템플릿이라 받자마자 DB 를 볼 수 있어야 하고, 배포에서는 로그인이 지킨다. 쓰지 않는 배포는 공격 표면 자체를 없앤다. 세션은 /admin 하위 앱 전용이라 API 의 Bearer 계약과 섞이지 않는다(admin-login ADR-001~006 — ADR-045 ③ 의 확인 플래그를 대체)
예시·빈 비밀값, 짧은 키, access==refresh 는 test 외 모든 ENV 에서 기동 거부. staging/production 은 DEBUG=true·LOG_LEVEL=DEBUG 도 거부 예시 키로 뜨면 누구나 토큰을 위조하고, debug 는 SQL 과 바인딩 값을 로그로 내보낸다. 잘못된 설정은 개발 단계부터 오류로 드러나야 .env 를 고친다(ADR-027·028·030·045)
.env 가 없으면 필수 값이 환경 변수로 와야 한다 코드 기본값은 유지하되 기본값만으로는 뜨지 않게 한다. 파일 없이 주입하는 컨테이너 배포는 통과(ADR-045 ①)
응답 직렬화는 FastAPI 기본(Pydantic) ORJSONResponse 는 이득이 없고 0.141 에서 deprecated. 제거 전후 응답 바이트 동일 확인
템플릿 프로필 분리(minimal/api-db/production) 보류 세 벌을 유지하는 비용이 크다. "무겁다" 는 피드백이 반복되면 선택 기능을 걷어내는 스크립트 쪽으로 재검토
라우트 검사는 app.openapi() 기준 FastAPI 0.141 부터 app.routes 가 하위 라우터를 평탄화하지 않는다(_IncludedRouter)
비밀번호는 Argon2id(pwdlib), 기존 bcrypt 는 로그인 시 재해시 FastAPI 공식 문서의 현행 권장. 평문이 없어 일괄 이전은 불가능하다(service-hardening ADR-013)
refresh 는 회전 + 재사용 탐지(Redis GETDEL), access 는 짧은 만료 탈취된 refresh 로 만료까지 재발급되던 구멍을 닫는다. access 즉시 폐기는 비목표 — 15분 만료로 대신한다(service-hardening ADR-014·015)
로그인·가입 레이트 리밋은 Redis 고정 창 + 라우트 의존성 명령 세 개로 끝나는 가장 단순한 방식. 창 경계 버스트는 수용(service-hardening ADR-016)
인가는 토큰만으로 만드는 Principal + 슈퍼유저/일반 2단계 + OwnershipPolicy 한 클래스 기능끼리 import 하지 않고(core 하나만 의존) 요청마다 DB 왕복이 없다. 권한 회수는 access 만료(15분)까지 늦다(service-hardening ADR-017·018)
여러 기능이 쓰는 인증 provider·PasswordHasher 는 core user 가 auth 를 import 하는 지름길 대신 core 로 올린다(service-hardening ADR-026)
