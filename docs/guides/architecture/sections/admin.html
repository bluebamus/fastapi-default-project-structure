12. SQLAdmin

아키텍처의 세부 주제입니다. 목적·책임·운영 및 확장 시 지켜야 할 계약을 설명합니다.

12. SQLAdmin

main.py (ADMIN_DISABLED 가 아닐 때만 — true 면 이 모듈을 import 하지도 않는다)
  └─ register_admin(app, engine)          app/features/admin.py — main 이 아는 유일한 이름
       ├─ create_admin_interface(...)     Admin(app, engine, title, authentication_backend, templates_dir) = /admin 마운트
       │    └─ build_admin_auth_backend(app)   AdminAuthBackend 를 기존 provider 로 조립
       └─ register_admin_views(admin)     ADMIN_VIEWS 를 선언 순서대로 add_view
  • 세 함수(와 백엔드 조립 함수)는 SQLAdmin 공식 API 가 아니라 이 프로젝트의 조립 함수입니다. 생성 쪽은 앱·엔진·인증 백엔드·템플릿 위치(모두 Admin 생성 인자라 여기에만 넣을 수 있다)를, 등록 쪽은 뷰 목록만 압니다. 회귀 가드: tests/test_admin_wiring.py.
  • 로그인(admin-login ADR-001~003): /admin 은 활성 슈퍼유저만 들어갑니다. AdminAuthBackend (app/features/auth/admin_backend.py)가 SQLAdmin AuthenticationBackend 를 구현합니다 — login 은 레이트 리밋 (admin:rl:login: 키, AUTH_LOGIN_* 한도) → API 로그인과 같은 AuthService.authenticate(bcrypt→Argon2 재해시 포함) → is_superuser 확인 → session.clear() 후 user_id 만 저장하고 rotate_session 으로 세션 ID 를 바꿉니다. 그 앞에 CSRF 토큰 대조가 있습니다(아래). 실패 사유는 구분하지 않고(400), 한도 초과는 로그인 화면을 429 + Retry-After 로 다시 그립니다. authenticate 는 요청마다 DB 에서 활성·슈퍼유저를 확인하고, logout 은 세션을 비웁니다(→ Redis 키 삭제).
  • 관리 세션 = Redis 서버 세션(admin-session-hardening ADR-001) — app/core/security/admin_session.py 의 AdminSessionStore(저장·조회·삭제·사용자 단위 폐기)와 RedisSessionMiddleware(scope["session"] 에 dict — request.session 인터페이스 그대로). 쿠키 admin_session 에는 무작위 세션 ID(secrets.token_urlsafe(32))만 있고, 내용은 admin:sess:{HMAC-SHA256(SESSION_SECRET_KEY, sid)} → JSON {"data", "user_id", "created_at"}, 사용자별 인덱스 admin:user_sessions:{user_id}(SET). 만료는 절대(ADMIN_SESSION_MAX_AGE_SECONDS, 연장 없음)와 미사용 (ADMIN_SESSION_IDLE_SECONDS, 요청마다 TTL 갱신·절대 만료 이내) — 기본값은 README 세션·토큰 만료. 기존 세션 저장은 SET XX 라 요청 도중 폐기된 세션을 응답이 되살리지 않습니다. 쿠키: Path=/admin, SameSite=Strict, HttpOnly, Max-Age=절대 만료, staging/production 은 Secure. 쿠키의 ID 가 Redis 에 없으면 빈 세션 + 쿠키 삭제. Redis 장애는 503(fail-closed). 미들웨어는 SQLAdmin 하위 앱에만 있어 API 인증과 섞이지 않습니다(tests/test_admin_session_scope.py). Redis 는 _app_redis(app) 로 바깥 앱의 것을 요청마다 받습니다(lifespan 이 연 뒤에야 있다).
  • 즉시 폐기(ADR-002) — 비활성화·슈퍼유저 강등·삭제 시 그 사용자의 관리 세션을 모두 지웁니다(다른 브라우저 포함). API 경로는 UserService 가 refresh 토큰 revoke_user 와 같은 자리에서 주입된 AdminSessionStore.revoke_user 를 부르고 (get_admin_session_store — ADMIN_DISABLED=true 면 None), 관리 화면 경로는 UserAdmin.on_model_change· on_model_delete(sqladmin 의 커밋 전 훅, ADR-007)가 이 요청의 저장소(request_session_store)로 부릅니다 — 수정은 변경 전 모델과 저장할 값을 revocations 하나로 비교해 두 집합을 정합니다 — API refresh 토큰은 비활성화·비밀번호 해시 변경·삭제 (UserService 와 같은 집합), 관리 세션은 그 집합 + 슈퍼유저 해제(ADR-009). 일반 수정은 아무것도 폐기하지 않습니다. 폐기가 실패하면(Redis) 커밋 전이라 변경도 저장되지 않습니다. 자기 자신을 강등하면 현재 세션도 끊깁니다. 매 요청 DB 확인은 이중 방어로 남깁니다.
  • CSRF(ADR-003·004) — AdminCsrfMiddleware(하위 앱, 세션 미들웨어 안쪽)가 /admin 의 POST·PUT·PATCH·DELETE 전부 (로그인·로그아웃 포함)에서 세션의 csrf_token 과 요청 토큰(헤더 X-CSRF-Token 또는 폼 필드 csrf_token)을 hmac.compare_digest 로 대조합니다. 폼 본문은 버퍼링해 읽고 같은 바이트를 sqladmin 에 다시 흘립니다 — 본문 10 MiB 초과는 413(Content-Length 로 먼저, 없거나 거짓이면 읽는 도중 누적 크기로), 필드 하나 1 MiB 초과·깨진 폼은 400(e2e-policy-2 결정 7, 상수 MAX_FORM_BODY_BYTES·MAX_FORM_FIELD_BYTES). 실패는 403 — 로그인 POST 는 로그인 화면(새 토큰), 그 밖은 관리 화면 오류 화면(AdminAuthBackend.csrf_rejected). 엔드포인트보다 먼저라 위조 로그인 POST 는 레이트 리밋·자격 확인에 닿지 않습니다(security-ops-hardening ADR-004 의 검사를 여기로 옮겼다). 화면은 app/templates/admin/sqladmin/base.html 이 원본(sqladmin_original/base.html)을 확장해 <meta name="csrf-token"> 과 인라인 스크립트(POST 폼 hidden 필드, 같은 출처 fetch/XHR 헤더, 로그아웃 링크 → POST 폼)를 더합니다. 로그아웃 라우트는 _logout_post_only 가 POST 전용으로 바꿔 끼워 GET 은 405 입니다. sqladmin 을 올릴 때 원본 블록·로그아웃 링크가 바뀌면 tests/test_admin_csrf.py 의 드리프트 검사가 실패합니다. sqladmin @action(GET 으로 상태 변경)은 쓰지 않습니다(테스트로 고정).
  • 로그인 화면 — app/templates/admin/sqladmin/login.html(Bootstrap 5.3.8 CSS, jsDelivr + SRI, JS 없음, hidden csrf_token)이 SQLAdmin 기본 화면을 덮어씁니다. templates_dir 의 FileSystemLoader 가 패키지 템플릿보다 먼저 찾아지기 때문입니다.
  • 끄기 — ADMIN_DISABLED=true 면 sqladmin·백엔드·세션 미들웨어·관리 세션 저장소를 만들지 않고 /admin 이하가 404 이며, 앱 응답·기동 로그에 경로가 나오지 않습니다(tests/test_admin_disabled.py). 예전 ADMIN 설정이 남아 있으면 기동을 거부합니다(§6.1).
  • 흐름도·쿠키 구조·위협 모델·운영 문제 해결은 관리 화면 인증 안내서가 원본입니다.
  • ModelView 는 기능이 소유합니다(app/features/<name>/admin.py 의 admin_views). 취합은 명시 import 입니다 — 예전의 getattr(module, "admin_views", []) 수집은 빈 admin.py 를 조용히 건너뛰었습니다. ADMIN_VIEWS 는 기능명 사전순이며 테스트가 순서까지 대조합니다. 모델이 있는 기능은 admin.py 를 가져야 합니다.
  • 기능 __init__.py 로 admin_views 를 재노출하지 않습니다 — 재노출하면 라우터 import 만으로 sqladmin 이 로드되어 ADMIN_DISABLED=true 가 "라우트만 안 붙임" 이 됩니다(ADMIN_DISABLED=true 미로드 검사).
  • column_filters 에는 sqladmin.filters 객체(BooleanFilter·OperationColumnFilter)를 넣습니다 — 모델 컬럼을 그대로 넣으면 sqladmin 0.32 의 목록 화면이 500 입니다. 생성 시각(UTCDateTime)에는 sqladmin 연산 필터 대신 LocalDateFilter (app/core/admin_filters.py, 템플릿 app/templates/admin/sqladmin/filters/local_date_filter.html)를 겁니다 — 날짜 YYYY-MM-DD 를 TIME_ZONE 의 로컬 자정으로 해석해 UTC aware 범위로 질의하고(같은 날 / 이후(포함) / 이전(미포함)), 빠른 선택(오늘·최근 7일·최근 30일)을 함께 그립니다. 기간(admin-session-hardening ADR-005) 연산 between 은 값 YYYY-MM-DD~YYYY-MM-DD 를 양 끝 포함(시작일 0시 ≤ t < 종료일 다음날 0시)으로 질의하고, 한쪽만 주면 열린 구간입니다 — sqladmin 이 값 하나만 넘기므로 필터 템플릿의 두 번째 폼이 날짜 입력 두 개를 합쳐 보냅니다. 형식이 틀린 입력·역순 기간은 필터를 적용하지 않고 WARNING 만 남깁니다(500 아님). created_at 이 있는 모든 뷰가 이 필터를 가집니다(security-ops-hardening ADR-005). 모든 뷰의 목록·필터·상세 화면은 tests/test_admin_views_render.py 가 로그인 상태로 확인합니다(admin-login F-005).
  • 배포 전 확인은 README 운영 배포 체크리스트에 있습니다.
  • User 뷰는 hashed_password 를 목록·상세·폼·내보내기에서 제외하고 can_create = False 입니다 (비밀번호 없이 만든 계정은 로그인할 수 없습니다). 이 제외 설정을 지우면 해시가 노출됩니다 (tests/core/test_admin_views.py).
