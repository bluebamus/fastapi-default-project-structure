3. 요청 처리 흐름

아키텍처의 세부 주제입니다. 목적·책임·운영 및 확장 시 지켜야 할 계약을 설명합니다.

3. 요청 처리 흐름

3.1 한 요청의 경로

요청 → UserInfoMiddleware → CORSMiddleware → 라우트
     → Depends: 세션 의존성(get_writer_db_session / get_read_only_db_session)
              → 기능 의존성 get_<name>_service[_readonly] → Service(db_session)
     → View 본문: Service 유스케이스 호출 → (쓰기면) await service.commit() → 응답 DTO
     → 응답 → UserInfoMiddleware 가 접속 로그 저장 태스크 제출 (§10)
     → 의존성 teardown: 세션 close (닫히면서 ROLLBACK 이 나간다)
계층 하는 일 하지 않는 일
View(api/routers/v1) 파라미터·본문 수신, Service 호출, 쓰기 커밋, 응답 DTO 변환, OpenAPI 메타데이터 SQL, AsyncSession 직접 주입, 복잡한 도메인 분기
Dependency 세션 선택 + Service(db_session) 조립 후 반환(yield 아님) 유스케이스 실행, 커밋
Service(BaseService) 유스케이스·비즈니스 규칙, 같은 세션으로 Repository 조립 HTTP 객체, SQL 문자열, 커밋 시점 결정
Repository ORM 쿼리 또는 Raw SQL, flush 까지 커밋, HTTP 응답, 비즈니스 규칙
Schema 입력 검증·응답 공개 필드·문서 DB 접근

미들웨어는 나중에 등록한 것이 바깥이라 UserInfoMiddleware 가 가장 바깥입니다. 같은 요청 안에서 같은 의존성 함수는 FastAPI 기본(use_cache=True)으로 한 번만 실행되지만, writer 와 read-only 는 다른 함수라 서로 다른 세션입니다.

3.2 트랜잭션 경계 — 쓰기 핸들러가 커밋한다

# dependencies — 조립만
async def get_catalog_service(
    db_session: AsyncSession = Depends(get_writer_db_session),
) -> CatalogService:
    return CatalogService(db_session)

# View — 응답 DTO 검증 → 커밋(한 번) → 반환
async def create_product(payload: ProductCreate, service: CatalogService = Depends(get_catalog_service)):
    product = await service.create_product(payload)
    response = ProductResponse.model_validate(product)
    await service.commit()
    return response
  • 성공: View 본문이 응답 DTO 를 검증한 뒤 응답을 반환하기 전에 await service.commit() (TX-004). 모든 쓰기 핸들러(catalog·blog·reply·sns·user·auth)가 이 순서이며, DTO 검증이 실패하면 커밋 0회로 500 이 됩니다(tests/test_write_dto_before_commit.py). reports 스냅샷 적재는 Service 가 커밋 전에 응답 DTO 를 만들어 돌려줍니다.
  • 예외: 커밋이 실행되지 않고 예외는 그대로 올라갑니다. 롤백은 async with 종료가 맡습니다 — AsyncSession.__aexit__ 이 shield 로 감싼 close() 를 실행하고 close() 가 ROLLBACK 을 보냅니다(ADR-031).
  • 조회: _readonly 의존성 → get_read_only_db_session, 커밋 0회(TX-002).
  • 요청 밖(background·Celery): async with background_db_session() as db_session: 에서 호출자가 직접 커밋합니다(별도 풀).

왜 의존성이 아니라 핸들러인가. 예전에는 의존성이 yield 뒤에서 커밋했습니다. FastAPI 0.141 로 올리자 기본 request scope 의 yield 의존성 종료 코드가 응답 전송 후 실행되어, 커밋이 실패해도 클라이언트가 201 을 받았습니다(scope="function" 은 종료 시점이 다릅니다 — 공식 설명). 커밋을 핸들러 본문으로 옮겨 실패가 응답 코드에 반영되게 했습니다. 구조 증거: tests/test_read_path_no_commit.py, app/features/blog/tests/test_transaction_boundary.py.

DB 커밋과 HTTP 전송은 하나의 원자적 작업이 아닙니다. 커밋 뒤 연결이 끊기거나 직렬화가 실패할 수 있으므로, 중복이 치명적인 생성 업무는 idempotency 정책을 따로 정합니다(DEVELOPMENT §4).

3.3 예외와 오류 응답

main.py 의 핸들러 4종(+ Redis 연결 오류 503)이 모든 오류를 ErrorResponse(error_code·message·detail)로 바꿉니다.

예외 응답
AppException 과 하위(NotFoundException·DuplicateException·DatabaseException…) 예외가 가진 상태 코드·error_code. 로그는 4xx 면 WARNING(detail 없음), 5xx 면 ERROR(detail 포함) — service-hardening ADR-008 ④
RequestValidationError 422, detail 에 field·message·type 목록. OpenAPI 의 422 도 이 ErrorResponse 로 광고한다 — FastAPI 기본 HTTPValidationError 는 앱 생성 시 후처리(main._openapi_with_actual_422)로 바꾼다(e2e-policy-2 결정 1, tests/test_openapi_contract.py)
Starlette HTTPException 해당 코드, error_code=HTTP_<코드>
redis ConnectionError·TimeoutError 503 SERVICE_UNAVAILABLE(fail-closed — 요청은 거부, 내부 정보 없음). 로그는 ERROR [RedisUnavailable] + traceback 한 번. 정상 응답으로 끝나 keep-alive 연결이 유지된다 — 아래 Exception 핸들러는 Starlette ServerErrorMiddleware 에 걸려 응답 뒤 예외를 다시 던지므로(uvicorn 이 traceback 을 한 번 더 남기고 연결을 닫는다) 그리로 보내지 않는다. 명령 오류(ResponseError 등)는 500 그대로 (integration-e2e ADR-009)
그 밖의 Exception 500 INTERNAL_SERVER_ERROR. DEBUG=true 면 detail 에 예외 문자열이 실린다 — 로그와 같은 redact() 로 비밀값을 가린 뒤(log-redaction ADR-001)

AppException·HTTPException 핸들러는 예외의 headers 를 응답에 그대로 싣습니다 — 405 Allow(라우팅이 채운다), 401 WWW-Authenticate: Bearer, 429 Retry-After(log-redaction ADR-002, tests/test_exception_headers.py). 401 은 예외가 헤더를 싣지 않았어도 두 핸들러가 WWW-Authenticate: Bearer 를 보탭니다(main._with_bearer_challenge) — 로그인 실패(InvalidCredentialsException)·refresh·logout·틀린 토큰(InvalidTokenException)까지 모든 401 이 같다(e2e-policy-2 결정 3). 405 의 Allow 는 Starlette 가 처음 걸린 라우트의 메서드로 채웁니다 — 같은 경로를 메서드별 함수로 나눈 곳 (GET·POST /api/v1/blog/posts)에서는 그 경로의 메서드 전부가 아니라 하나만 실립니다.

핸들러는 JSONResponse(content=model.model_dump(mode="json")) 로 직렬화합니다 — detail 에 datetime·UUID 가 들어와도 깨지지 않게 하기 위해서입니다(tests/test_response_serialization.py). 일반 응답은 response_model 을 통해 Pydantic 이 직접 JSON 을 만듭니다(커스텀 응답 클래스 없음). startup 예외는 HTTP 핸들러가 처리하지 않습니다(§7.3).

경로 의미
GET /health 프로세스 생존과 VERSION. 외부 연결을 검사하지 않는다 (liveness)
GET /ready ping_writer_db()(writer 엔진에서 SELECT 1)와 Redis PING(get_redis 로 주입받은 lifespan client)을 동시에, 각각 2초(READINESS_TIMEOUT_SECONDS) 안에 실행한다. 하나라도 실패·초과면 503. 응답에는 원문이 없고, 서버 로그에는 대상(DB·Redis)과 예외 타입만 남긴다(DSN·호스트·드라이버 원문 비노출). client 가 없으면(lifespan 밖) provider 가 503 (service-hardening ADR-011)
