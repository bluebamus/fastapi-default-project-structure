11. 인증 (JWT)

아키텍처의 세부 주제입니다. 목적·책임·운영 및 확장 시 지켜야 할 계약을 설명합니다.

11. 인증 (JWT)

OAuth2 password flow + JWT access/refresh 토큰(service-hardening ADR-013~018·ADR-025·ADR-026). 자격증명은 user 기능의 User.hashed_password 에 두고, auth 기능(app/features/auth/)이 흐름(AuthService)을, app/core/security/ 가 여러 기능이 쓰는 부품(해시·토큰·회전 저장소·레이트 리밋·인증 주체·소유권 정책과 그 provider)을 맡습니다.

메서드·경로 인증 요청 성공 실패
POST /api/v1/auth/register — JSON (username·email·password 8~128자) 201 409 중복 · 422 · 429
POST /api/v1/auth/login — form (username·password) 200 401 · 422 · 429
POST /api/v1/auth/refresh — JSON (refresh_token) 200 401 · 422
POST /api/v1/auth/logout — JSON (refresh_token) 204 401 · 422
GET /api/v1/auth/me Bearer — 200 401 
curl -X POST localhost:8000/api/v1/auth/register -H 'Content-Type: application/json' \
  -d '{"username":"alice","email":"alice@example.com","password":"secret-pw-1234"}'
curl -X POST localhost:8000/api/v1/auth/login -d 'username=alice&password=secret-pw-1234'
# → {"access_token":"eyJ...","refresh_token":"eyJ...","token_type":"bearer","expires_in":900}
curl localhost:8000/api/v1/auth/me -H 'Authorization: Bearer <access_token>'
curl -X POST localhost:8000/api/v1/auth/refresh -H 'Content-Type: application/json' \
  -d '{"refresh_token":"<refresh_token>"}'          # 새 쌍. 보낸 refresh 는 이제 못 쓴다
curl -X POST localhost:8000/api/v1/auth/logout -H 'Content-Type: application/json' \
  -d '{"refresh_token":"<refresh_token>"}'          # 204

조립(주입) — 협력 객체는 모두 생성자로 받고 provider 가 만듭니다(service-hardening C-1). 여러 기능이 쓰는 provider 는 core 의 app/core/security/dependencies.py, auth 전용은 auth_dependencies.py 에 있습니다.

# core (app/core/security/dependencies.py)
get_password_hasher()                                # 프로세스 단일(lru_cache) — auth·user
get_token_service()                                  # TokenService(jwt_settings) — 발급(auth)·검증(principal)
get_refresh_token_store(redis=get_redis)             # RefreshTokenStore(refresh TTL) — auth 회전·user 폐기
get_ownership_policy()                               # OwnershipPolicy — blog·sns·reply·user
get_current_principal(request, token=oauth2_scheme, tokens=get_token_service) -> Principal   # DB 조회 없음
require_superuser(principal=get_current_principal)   # 403
# core (app/core/security/access.py) — 뷰가 dependencies=[...] 에 넣는 접근 수준(§11.2)
Public / PublicWrite                                 # 표식(아무것도 안 함) — 인증 없는 조회 / 쓰기
LoginRequired = Depends(get_current_principal)       # 401
SuperuserRequired = Depends(require_superuser)       # 401 / 403
AccessPolicyGuard().verify(app)                      # main.py 조립 끝 — 선언 없거나 모순되면 기동 거부
# auth
get_auth_service(session=get_writer_db_session, hasher, tokens, store)
login_rate_limit / register_rate_limit               # RateLimiter(get_redis) + ClientIPResolver
get_current_user(principal=get_current_principal, session=get_read_only_db_session)   # /me — 엔티티 필요

테스트는 dependency_overrides[get_redis] 에 fakeredis 를 넣으면 회전 저장소·레이트 리밋이 함께 바뀝니다.

비밀번호 — PasswordHasher (app/core/security/password_hasher.py — auth 의 가입·로그인과 user 의 관리자 생성이 함께 쓴다, ADR-026) - 새 해시는 Argon2id(pwdlib). 이전 버전의 bcrypt 해시($2 접두사)는 그때 규칙(UTF-8 72바이트 절단)으로 검증하고, 맞으면 Argon2 로 다시 해시해 로그인 핸들러가 커밋합니다(점진 이전 — 그 밖의 로그인은 커밋하지 않습니다). - 상수 시간 인증: 사용자가 없거나 비밀번호가 없어도 더미 Argon2 해시로 같은 비용을 치릅니다. 논블로킹 해싱: 해시·검증은 asyncio.to_thread 에서 돕니다.

토큰 — TokenService (app/core/security/tokens.py) - claims sub, type, iat, nbf, exp, jti(uuid4 hex), iss, aud + access 는 username·su(슈퍼유저 여부), refresh 는 fam(회전 family). access 의 username·su 는 필수입니다 — su 가 없는 토큰(인가 도입 전 발급분)은 401 이고 다시 로그인하면 됩니다. - 검증: 알고리즘은 설정 하나(algorithms=[JWT_ALGORITHM]), iss·aud 일치, 위 claim 전부 필수, leeway, type 일치. access·refresh 는 서명 키도 다릅니다. 실패는 사유와 관계없이 InvalidTokenException(401, AUTH_INVALID_TOKEN).

회전·폐기 — RefreshTokenStore (app/core/security/refresh_store.py, Redis)

키 값 · TTL 쓰임
auth:rt:{jti} {"sub","fam"} · refresh 만료 아직 안 쓴 refresh. 회전 시 GETDEL 로 소비
auth:user:{sub}:fams family 집합 · refresh 만료 사용자 단위 폐기(revoke_user)
auth:fam:{fam}:revoked 1 · refresh 만료 폐기된 family
  • refresh: 서명 검증 → family 폐기 여부 → GETDEL 로 jti 소비. 값이 없으면 재사용(이미 쓴 토큰)이라 family 를 폐기하고 401 — 그 사이 발급된 새 refresh 도 함께 막힙니다. 사용자가 없거나 비활성이어도 family 폐기 후 401. GETDEL 하나가 원자적이라 같은 토큰으로 동시에 회전해도 한쪽만 성공합니다.
  • logout: family 폐기, 204. 이미 폐기됐어도 204(멱등). access 토큰은 폐기하지 않습니다 — 만료(기본 15분)까지 유효합니다.

레이트 리밋 — RateLimiter (app/core/security/rate_limit.py, Redis 고정 창) - MULTI 안에서 SET key 0 EX window NX → INCR → TTL. 창은 첫 hit 에 시작하고 이후 hit 이 늘리지 않습니다. - 로그인: auth:rl:login:{ip}:{username 소문자}(기본 5회/60초)와 auth:rl:login:{ip}(20회/60초). 성공하면 앞의 키만 지웁니다. 회원가입: auth:rl:register:{ip}(5회/3600초). IP 는 접속 로그와 같은 ClientIPResolver(TRUSTED_PROXY_HOPS, §10). 관리 화면 로그인은 같은 한도를 admin:rl:login:{ip}:{username}·admin:rl:login:{ip} 로 따로 셉니다(§12). 프록시 뒤 배포는 TRUSTED_PROXY_HOPS 를 앞단 프록시 단 수로 설정합니다 — 0 이면 모든 클라이언트가 프록시 IP 하나로 보여 IP 한도가 전체 사용자에게 함께 걸리고, 실제보다 크게 잡으면 IP 를 위조할 수 있습니다. - 초과는 TooManyRequestsException — 429 + Retry-After(창이 끝날 때까지 초). AppException.headers 를 전역 핸들러가 싣습니다.

설정 기본값

  • 비활성 사용자(is_active=false)는 로그인·회전·me 에서 막힙니다. 비활성화·삭제는 revoke_user 로 refresh 를 모두 폐기합니다.
  • get_current_user 는 get_current_principal 위에서 읽기 세션(primary 고정, §4.3)의 UserRepository 로 조회합니다 — Redis 를 쓰지 않습니다.

11.1 인가 — Principal · 슈퍼유저 · 소유권

인가는 슈퍼유저/일반 2단계입니다(service-hardening ADR-017·018). RBAC 세분화는 비목표입니다.

  • Principal(id, username, is_superuser) (app/core/security/authorization.py, frozen dataclass) — access 토큰의 sub·username·su 로만 만듭니다. 요청마다 DB·Redis 왕복이 없고, 기능은 사용자 모델 대신 이 값 하나에 기댑니다. get_current_principal 이 만들고 request.state.user_id 를 채웁니다 — 접속 로그 미들웨어가 응답 뒤에 읽어 user_access_logs.user_id 에 남깁니다(§10).
  • 별칭 — 인자용 CurrentPrincipal(로그인)·SuperuserPrincipal(슈퍼유저), 데코레이터용 접근 수준 LoginRequired·SuperuserRequired·Public·PublicWrite(§11.2 — 뷰마다 하나 선언, 없으면 기동 거부). 토큰 문제는 401(WWW-Authenticate: Bearer), 권한 부족은 403 FORBIDDEN.
  • OwnershipPolicy.ensure_can_modify(owner_id, principal) — 소유자 본인 또는 슈퍼유저만 통과. owner_id 가 None (인가 도입 전 행)이면 슈퍼유저만. blog·sns·reply·user 서비스가 생성자로 받고 수정·삭제(user 는 단건 조회 포함) 메서드가 principal 을 받아 부릅니다. 존재 확인(404)이 먼저이고 user 만 반대로 권한이 먼저입니다(남의 ID 로 계정 존재를 캐지 못하게).
  • 스키마 — users.is_superuser(기본 false), blog·sns·reply 의 author_id(String(36), NULL, 인덱스, FK 없음 — 기능 모델끼리 참조하지 않는다). 리비전 c9e1a3b5d7f0. 작성자(author·author_id)는 생성 시 서버가 주체로 채우고 수정 스키마에 없습니다.
기능 조회 생성 수정·삭제
blog·sns·reply Public 인자 CurrentPrincipal 인자 CurrentPrincipal + OwnershipPolicy
catalog Public SuperuserRequired SuperuserRequired
reports·home(접속 로그) 뷰마다 SuperuserRequired 〃 —
user 목록 SuperuserRequired · 단건 인자 CurrentPrincipal + OwnershipPolicy SuperuserRequired(비밀번호 필수) 수정 인자 CurrentPrincipal + OwnershipPolicy + is_active·is_superuser 는 슈퍼유저 · 삭제 SuperuserRequired
auth /me — get_current_user(안에서 get_current_principal) register·login·refresh·logout 은 PublicWrite —
health·ready Public — —
  • 첫 슈퍼유저 — python -m scripts.create_superuser(scripts/create_superuser.py). background_db_session + core 의 get_password_hasher + UserRepository 로 조립해 만들거나 승격하고 한 번 커밋합니다. 비밀번호는 getpass 또는 --password-stdin 으로만 받습니다(환경 변수를 읽지 않는다 — 설정 계약). 이 계정이 관리 화면(/admin) 로그인 계정이기도 합니다.
  • SQLAdmin 은 이 인가 밖입니다(§12) — /admin 은 JWT 가 아니라 활성 슈퍼유저의 Redis 서버 세션으로 들어가고, 그 세션은 API 를 인증하지 않습니다.

11.2 접근 수준 선언과 기본 거부

모든 API 뷰는 접근 수준을 하나 선언합니다(access-policy ADR-001~003). 경로 데코레이터의 dependencies=[...] 에 넣는 Depends 객체 넷이 app/core/security/access.py 에 있습니다.

수준 정체 쓰는 곳 실패
Public 아무것도 하지 않는 async 표식 함수 인증 없는 조회 — GET·HEAD·OPTIONS 만 —
PublicWrite 또 다른 표식 함수 인증 없는 쓰기를 의도적으로 연다 — 가입·로그인·refresh·logout —
LoginRequired Depends(get_current_principal) 로그인 401
SuperuserRequired Depends(require_superuser) 슈퍼유저 401 / 403
  • 판정 — AccessPolicyGuard.levels() 가 라우트의 의존성 트리(dependant)를 재귀로 훑어 위 호출 대상이 있는지 봅니다. 그래서 인자 principal: CurrentPrincipal/SuperuserPrincipal, 안에서 get_current_principal 을 쓰는 의존성(/me 의 get_current_user), 라우터 단위·include_router(dependencies=…) 선언도 같은 선언으로 인정됩니다. require_superuser 는 안에서 get_current_principal 을 쓰므로 둘이 함께 보이면 슈퍼유저로 접습니다.
  • 기본 거부 — main.py 가 라우터 include·health/ready·/docs·SQLAdmin 마운트를 마친 직후 AccessPolicyGuard().verify(app) 를 부릅니다. 위반이 하나라도 있으면 위반 전체 목록을 담은 AccessPolicyError(RuntimeError)로 main import 가 실패합니다(§7.3). 위반: ① 선언 없음 ② 서로 다른 수준 둘 이상(Public 계열 + 인증 계열 등) ③ 쓰기 메서드에 Public (→ PublicWrite 를 쓰라는 안내) ④ 안전한 메서드에 PublicWrite.
  • 대상 — fastapi.routing.iter_route_contexts(app.routes) 로 FastAPI 0.141 의 _IncludedRouter 중첩을 펼친 모든 APIRoute. include_in_schema=False 인 경로(DEBUG 의 Scalar /docs)도 포함합니다. FastAPI 가 붙이는 문서 경로(Starlette Route)와 Mount(/admin — 자체 세션 인증, §12)는 APIRoute 가 아니라 빠집니다.
  • 함수를 감싸는 데코레이터는 쓰지 않습니다. FastAPI 는 핸들러 시그니처로 주입·검증·OpenAPI 를 만듭니다 — Django 식 @login_required 로 감싸면 그 시그니처가 가려집니다. 경로 데코레이터의 dependencies= 가 FastAPI 에서 "데코레이터로 거는" 방법이고, 데코레이터만으로는 생기지 않는 기본 정책을 기동 검사가 채웁니다.
  • OpenAPI — 401/403 응답 문서(UNAUTHORIZED_RESPONSES·FORBIDDEN_RESPONSES)는 종전대로 responses= 에 펼칩니다. home·reports 는 의존성만 뷰로 옮기고 responses=FORBIDDEN_RESPONSES 는 라우터 단위로 둡니다 — 생성되는 OpenAPI 는 바뀌지 않았습니다(security 표시 포함).
  • 테스트 — 가드 규칙은 tests/core/test_access_policy.py, 예시 정책은 tests/test_authorization.py 의 EXPECTED_ACCESS (유일한 기대 표 — 401/403 실요청 대상도 여기서 뽑는다), 조립 경로는 tests/test_main.py 의 test_main_refuses_to_start_when_a_view_declares_no_access_level(별도 프로세스에서 선언 없는 뷰를 더하면 import 실패).
